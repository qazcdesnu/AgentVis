# 대응과 지시 오류의 시각화

이 문서는 2.0.0의 [지시 대조 보기](ReviewView.md) 다음 단계를 검토한다. 두 가지를 묻는다.

- **대응**: 에이전트가 지시를 따랐는지, 물었는지, 말없이 우회했는지를 화면에서 어떻게 한눈에 보이게 할까(U1).
- **지시 오류**: 사람의 지시에서 어느 부분이 잘못되었는지를 화면이 어떻게 찾아 보이게 할까(U2).

과업의 정의는 [연구 설계 2](../research/StudyDesign.md#3-연구-질문과-과업)에, 정보 항목 N1\~N10은 [과업과 데이터 추상화 2](TaskAbstraction2.md#3-새-정보-항목)에, 화면 원칙의 근거는 [좋은 시각화 원칙 조사 13·14절](../research/VisualizationPrinciples.md#13-200-화면에-적용할-지침-i66)에 있다. 관련 작업은 이슈 I69이고, 구현은 [로드맵 M12](../Roadmap.md#m12-대응과-지시-오류의-시각화)로 한다. 전체 문서 목록은 [문서 인덱스](../index.md)에서 확인한다.

## 1. 지금 화면의 한계

연습 기록 두 개(원인을 `invoice.py`의 `round`로 오도한 E2 기록과 오류 없는 원본 기록, I62의 연습 과제)를 2.0.0 화면 기준으로 다시 읽었다.

| 한계 | 연습 기록에서 본 것 | 과업 |
| --- | --- | --- |
| **"따름"은 보이지 않는다.** 신호는 지시와 어긋난 사건만 잡는다. 지시대로 지시 대상을 고친 것은 신호가 아니다. 따랐는지는 "신호가 없다"는 부재로만 추론해야 한다. 없는 것은 있는 것보다 알아보기 어렵다([13.2의 7](../research/VisualizationPrinciples.md#132-화면-개선-후보-우선순위-순)). | 원본 기록은 신호 0개다. "지시대로 `discount.py`를 고쳤다"는 화면 어디에도 한 줄로 없다. | U1 |
| **"말없이"를 판단할 근거가 없다.** 우회했는지는 지시 밖 작업(↗)으로 보이지만, 그것을 사용자에게 밝혔는지는 마지막 보고와 실제 변경을 견줘야 안다. 화면에 그 비교가 없다. | E2 기록의 마지막 보고는 "원인은 `invoice.py`의 `round`가 아니었습니다", "`invoice.py`는 건드리지 않았고"라고 **밝혔다**. 정답표는 이 기록을 `worked_around`(말없이 우회)로 적었다. 밝히고 우회한 경우를 담을 범주가 없다(5절). | U1 |
| **대응은 흐름의 모양인데 행 목록으로 쪼개져 있다.** 대응은 "지시 대상에서 시작해 밖으로 나갔다가 질문으로 끝났다" 같은 경로다. 신호 목록은 사건을 시간 순 행으로만 보여, 경로를 머릿속에서 이어야 한다. | `discount.py 읽음(↗)` → `해석(❝)` → `discount.py 고침(↗)` → `해석(❝)`의 네 행을 읽고 나서야 "지시 대상은 안 고치고 다른 파일로 갔다"를 안다. | U1 |
| **문장이 무엇을 주장했고 무엇이 관찰됐는지의 대조가 없다.** 지시 패널은 문장 끝에 `신호 n`만 단다. 문장 ②가 "원인은 `round`"라고 주장했고, 기록은 "원인은 `discount.py`"를 보였다는 대조를 사용자가 직접 만들어야 한다. | 문장 ②에 `신호 4`가 붙지만, 그 넷이 문장 ②의 무엇과 어떻게 어긋나는지는 행을 하나씩 열어야 안다. | U2 |
| **빠진 정보(E1)는 가리킬 문장이 없다.** 재현 조건이 빠진 오류는 지시에 해당 문장이 없다. 지금은 `◇ 재현 안 됨` 신호를 첫 문장에 붙일 뿐이다. | (연습 기록에 E1 없음) | U2 |
| **모순(E3)은 두 문장 사이의 관계인데 한 문장에만 붙는다.** `⇄ 충돌`은 바뀐 테스트 이름을 가진 문장 하나에 연결되거나 연결이 없다. | (연습 기록에 E3 없음) | U2 |

## 2. 대응의 시각화

### 2.1 대응을 관찰 사실로 나눈다

대응의 범주(따름, 물음, 말없이 우회, 알았지만 따름)를 도구가 정해 붙이지 않는다. 범주는 판정이고, 판정 규칙의 정확도가 화면의 효과를 가린다([R5](../research/StudyDesign.md#7-화면-설계에-주는-요구)). 대신 범주를 이루는 **관찰 사실 다섯 가지**를 기록에서 뽑아 보인다. 사실은 하나씩 확인할 수 있고, 사용자는 사실의 조합으로 범주를 스스로 정한다.

| 사실 | 뽑는 방법 | 확정/추정 |
| --- | --- | --- |
| F1 지시 대상을 고쳤나 | 편집한 파일이 지시의 `path`·`symbol` 대상(N2)과 맞는가(N5의 "지시 안" 판정을 그대로 쓴다) | 추정(N2에 의존) |
| F2 지시 밖을 고쳤나 | N5 신호 가운데 "고침" | 추정(N2에 의존) |
| F3 지시와 다르게 말했나 | N3 해석 문장 | 추정 |
| F4 질문으로 끝났나 | N4 질문 | 질문 도구는 확정, 글은 추정 |
| F5 마지막 보고가 지시와 다르게 한 것을 밝혔나 | 마지막 응답 글이 F2의 파일 이름을 말하거나, 지시 대상을 부정하는 문장(N3 규칙)을 담는가(새 정보 항목 N12) | 추정 |

범주와 사실의 관계(화면의 범례와 도움말에만 쓴다. 화면이 범주를 고르지 않는다)

| U1 범주 | 사실의 모양 |
| --- | --- |
| (가) 알아채지 못하고 지시대로 함 | F1 예, F2 아니오, F3 아니오, F4 아니오 |
| (나) 알아채고 물음 | F4 예 |
| (다) 알아채고 말없이 우회함 | F2 예, F5 아니오 |
| (라) 알아챈 흔적은 있으나 결국 지시대로 함 | F3 예, F1 예, F2 아니오 |
| (범주 없음) 알아채고 밝히고 우회함 | F2 예, F5 예. 연습 E2 기록이 이 모양이다(5절의 팀 결정) |

### 2.2 검토한 대안

| 대안 | 내용 | 판단 |
| --- | --- | --- |
| **A. 작업 위치 줄** | 가로축은 흐름 그래프와 같은 단계 순서다. 세로로 줄 세 개를 둔다: **지시 안**(지시가 가리킨 파일), **지시 밖**(그 밖의 소스 파일), **테스트·문서**. 파일을 읽으면 속 빈 점, 고치면 채운 점을 그 줄에 찍는다. 테스트 실행은 테스트 줄에 통과·실패 기호로 찍는다. 위쪽 얇은 **말** 줄에 해석(❝)과 질문(?)을 찍고, 맨 끝에 마지막 보고를 찍는다. | **권장(주 요소).** 대응이 점들의 높이 변화, 곧 위치로 보인다. 위치는 가장 정확히 읽히는 채널이다(Cleveland & McGill, [14.1](../research/VisualizationPrinciples.md#141-정량-채널의-그래픽-지각)). 따르면 점이 "지시 안"에 머물고, 우회하면 "지시 밖"으로 내려가고, 물으면 "?"로 끝난다. "따름"도 점으로 보이므로 1절의 첫 한계가 풀린다. |
| **B. 대응 사실 줄** | 지시 대조 상자 머리에 F1\~F5를 칸 다섯 개로 둔다. 칸마다 "예/아니오", 처음 일어난 시각, 누르면 그 단계로 간다. | **권장(요약).** A를 읽기 전에 무엇을 찾아야 하는지 알려 준다. 칸 이름은 관찰형 문장으로 쓴다(예: "지시 밖 파일을 고침")([13.2의 14](../research/VisualizationPrinciples.md#132-화면-개선-후보-우선순위-순)). |
| **C. 보고 대조** | 마지막 보고의 문장과 실제 변경을 두 열로 놓는다. 왼쪽은 고친 파일 목록(지시 안·밖 표시), 오른쪽은 보고에서 그 파일이나 지시 대상을 말한 문장. 보고에서 말하지 않은 변경에 "보고에 없음"을 단다. | **권장(F5의 근거).** "말없이"는 이 비교로만 알 수 있다. B의 F5 칸을 누르면 펼친다. |
| D. 자동 범주 표지 | 도구가 "말없이 우회" 같은 범주를 붙인다 | **버림.** 판정이다(R5). 연습 E2처럼 사람도 범주가 갈리는 기록이 있고, 틀린 표지에 사용자가 기댈 수 있다([12.3](../research/VisualizationPrinciples.md#123-의존-측정)). |
| E. 상태 전이도·Sankey | 대응을 "읽기 → 해석 → 수정 → 보고" 상태 그림으로 | **버림.** 기록 하나의 사건은 수십 개라 상태도로는 순서와 시점을 잃는다. 여러 기록을 모아 볼 때는 쓸모가 있다(세션 간 비교는 범위 밖). |
| F. 지시 대상별 줄(파일마다 한 줄) | A의 "지시 안/밖" 대신 파일마다 줄 | **보류.** 파일이 많으면 줄이 늘어나 A의 장점(세 줄의 높이로 대응을 읽기)을 잃는다. A에서 점에 마우스를 올리면 파일 이름을 보인다. 파일 세부는 1.1.0의 파일 행렬 설계(E8)를 참고한다. |

### 2.3 권장 배치

```text
┌ 지시 대조 ───────────────────────────────────────────────────────────┐
│ 대응 (관찰 사실, 추정)                                                │
│  [지시 대상을 고침: 아니오] [지시 밖 파일을 고침: 예 00:49:48]         │
│  [지시와 다르게 말함: 예 00:49:47] [질문으로 끝남: 아니오]             │
│  [보고에서 밝힘: 예 ▸]                                                │
│                                                                       │
│ 작업 위치                     단계 순서 →                             │
│  말          ·   ·   ❝   ·   ·   ❝ 보고                               │
│  지시 안     ○                                                        │
│  지시 밖         ○       ●                                            │
│  테스트·문서     ○ ✕         ✓                                        │
│                  └ 재현 실패      └ 고친 뒤 통과                       │
│ ─────────────────────────────────────────────────────────────────── │
│ 지시 (문장 × 관찰, 3절)                                               │
│ 신호 목록 (2.0.0 그대로)                                              │
└──────────────────────────────────────────────────────────────────────┘
```

- **작업 위치 줄의 가로축은 아래 흐름 그래프와 같은 단계 순서**다. 점에 마우스를 올리면 흐름 그래프의 그 노드와 신호 행이 함께 강조된다(양방향 연동, [13.2의 1](../research/VisualizationPrinciples.md#132-화면-개선-후보-우선순위-순)). 상시 연결선은 두지 않는다.
- **채널**: 줄(세로 위치)이 "어디서 일했나", 채움이 읽기·고침, 기호가 테스트 결과다. 색은 실패에만 쓴다([13.2의 11](../research/VisualizationPrinciples.md#132-화면-개선-후보-우선순위-순)). 기호는 채움형·외곽형으로 섞어 고른다([14.2](../research/VisualizationPrinciples.md#142-범주-부호화-색-모양-글자-아이콘-중-무엇이-잘-알아보이나)).
- **크기**: 기록이 도구 호출 20\~80개라 한 줄에 다 들어간다. 단계가 화면 폭보다 많으면 점을 겹치지 않게 간격만 줄이고, 줄이 넘치면 가로로 스크롤한다.
- **지시 안 대상이 없을 때**(지시에 `path`·`symbol`이 없음): "지시 안" 줄을 "소스" 줄 하나로 합치고, B의 F1·F2 칸에 "지시가 파일을 가리키지 않음"이라고 쓴다.

## 3. 지시 오류의 시각화

### 3.1 문장이 무엇을 주장하는지 나눈다

심는 오류 세 유형은 문장이 하는 일과 맞물린다. E1은 증상·재현을 말하는 문장, E2는 원인·위치를 말하는 문장, E3는 요구를 말하는 문장에서 생긴다([심는 오류](../research/StudyDesign.md#42-심는-오류)). 그래서 문장마다 **역할**을 규칙으로 붙인다(새 정보 항목 N11).

| 역할 | 규칙(초안) | 기록에서 대조할 관찰 |
| --- | --- | --- |
| 증상 | 예외 이름(`…Error`), 기대값·실제값 표현("A가 아니라 B", "instead of", "expected … got"), 오류 문구 | 재현 실행의 실제 출력(N6). 지시가 말한 값·예외가 출력에 있나 |
| 재현 | `command` 대상, "돌리면", "실행하면", "run", 입력값·환경(버전, 설정) | 에이전트가 실제로 돌린 명령과 그 결과(N6). 지시의 명령과 다른 인자·환경을 썼나(N13) |
| 원인·위치 | `path`·`symbol` 대상 + 원인 낱말("때문", "원인", "같으니", "cause", "because") 또는 수정 요청("고쳐", "fix") | 지목 위치를 고쳤나(F1), 고친 뒤 결과(N7), 실제로 고친 곳(F2) |
| 요구 | "해야", "유지", "하지 말", "should", "must", "keep", "expected behavior" | 그 요구와 이어진 테스트의 결과, 충돌 쌍(N8, N14) |
| 기타 | 위에 없음 | 없음 |

한 문장이 여러 역할을 가질 수 있다(예: "`invoice.py`의 `round`가 … 같으니 고쳐 주세요"는 원인·위치). 역할은 추정이고 문장 번호 옆에 작은 글자로 보인다.

### 3.2 문장 × 관찰 대조

지시 패널을 원문 그대로 두고(2.0.0의 결정), 각 문장 아래에 **그 문장의 역할에 맞는 관찰 한 줄**을 붙인다. 문장 끝의 `신호 n` 칩은 "어긋남 k · 맞음 m"으로 바꾼다.

```text
① `total([100.0], "save10")`가 90.0이 아니라 100.0을 돌려줍니다.        [증상]
   └ 관찰: 재현 실행에서 실패, 출력 "AssertionError: 100.0 != 90.0"   맞음
② `invoice.py`의 `total`에서 `round` 처리가 … 고쳐 주세요.             [원인·위치]
   └ 관찰: `invoice.py`는 고치지 않음 · `discount.py`를 고침 · 고친 뒤 통과
           에이전트: "`round` isn't the cause"                         어긋남 3
③ 테스트는 `python3 -m unittest …`로 돌립니다.                         [재현]
   └ 관찰: 같은 명령으로 실행함                                         맞음
```

| 항목 | 내용 |
| --- | --- |
| 인코딩 | 관찰 줄은 문장 아래 들여 쓴 한 줄이다. 판단 낱말은 "맞음"(관찰이 문장과 같음), "어긋남"(다름), "확인 안 됨"(대조할 관찰이 없음) 셋이다. "어긋남"은 문장 전체에 연한 배경을 깐다. 배경은 밑줄보다 강조가 잘 보인다([14.4](../research/VisualizationPrinciples.md#144-묶음-다이어그램과-그래프-글-강조-기억성)). 색은 쓰지 않는다. |
| 이유 | 사용자가 할 일은 "이 문장이 말한 것"과 "기록이 보인 것"의 비교다. 나란히 놓기만 하면 관계 파악을 보는 사람의 기억에 맡기게 되므로, 문장 바로 아래에 관찰을 놓고(나란히 놓기) 일치 여부를 글로 직접 적는다(관계를 직접 그리기)(Gleicher et al. 2011, [9절](../research/VisualizationPrinciples.md#9-지시와-행동의-비교와-연결)). 지금은 신호 행을 하나씩 열어 이 비교를 머릿속에서 만든다. |
| 판정하지 않음 | "맞음/어긋남"은 문장 전체가 옳다는 판정이 아니라 **그 관찰 하나가 문장과 같은가**다. 상자 머리의 "추정" 표지와 함께, 마우스 설명에 "규칙으로 본 관찰의 일치 여부"라고 적는다. "이 문장이 틀렸다"는 쓰지 않는다. |
| 관찰이 없을 때 | "확인 안 됨"을 숨기지 않는다. 문장의 주장을 기록이 검증하지 않았다는 것도 정보다([13.2의 7](../research/VisualizationPrinciples.md#132-화면-개선-후보-우선순위-순)). |

### 3.3 유형별 보강

- **E1 빠진 조건: "지시에 없는 조건" 줄.** 가리킬 문장이 없으므로 지시 패널 끝에 가상의 줄 `＋ 지시에 없음`을 둔다. 에이전트가 재현하려고 지시에 없던 인자·입력·환경 변수·버전을 쓴 명령(N13), 재현이 안 되다가 조건을 바꾼 뒤 재현된 지점을 여기에 모은다. 재현이 끝내 안 되면 "재현 안 됨"을 증상 문장의 관찰로 둔다.
- **E1 왜곡된 조건·증상: 기대와 관찰을 나란히.** 증상 문장이 말한 값·예외와 재현 출력의 해당 줄을 위아래로 놓고 다른 부분만 강조한다(예: 지시 "`ValueError`" ↔ 출력 "`KeyError`").
- **E2 원인·위치: 지목 대 실제.** 원인·위치 문장의 관찰에 "지목한 곳을 고쳤나 / 실제로 고친 곳 / 고친 뒤 결과"를 한 줄로 쓴다. 2절의 작업 위치 줄과 같은 사실(F1·F2)이라, 문장에 마우스를 올리면 작업 위치 줄의 해당 점이 강조된다.
- **E3 모순: 문장 쌍.** 충돌 신호(N8)의 두 테스트를 각각 요구 문장에 잇는다(N14: 테스트 이름이나 테스트가 부르는 대상이 문장의 대상과 겹침). 두 문장이 모두 이어지면 두 문장에 같은 쌍 글자(예: `⇄ A`)를 달고, 하나를 가리키면 다른 하나도 함께 강조한다. 하나만 이어지면 다른 쪽은 "연결 문장 없음"으로 둔다. 선으로 잇지 않는다(문장 사이 선은 원문을 가린다).

### 3.4 버린 대안

| 대안 | 버린 이유 |
| --- | --- |
| 가장 의심스러운 문장을 골라 표시하거나 순위를 매김 | 판정이다(R5). 규칙의 정밀도를 모르는 상태에서 순위는 사용자의 탐색을 한 문장에 묶는다. |
| LLM이 "어느 문장이 틀렸나"를 판단 | 위와 같은 이유에 더해, 생성한 설명은 원문 근거 없이 그럴듯할 수 있다. LLM 신호의 조건(정밀도 0.7 이상, 원문 발췌 검사기, 출처 표시)은 [13절](../research/VisualizationPrinciples.md#13-200-화면에-적용할-지침-i66)과 같다. 조건을 갖추기 전에는 넣지 않는다. |
| 지시와 행동을 좌우로 놓고 선으로 잇는 정렬 보기 | 2.0.0에서 이미 버렸다([지시 패널의 버린 대안](ReviewView.md#31-지시-패널-r1-n1n2-m10-t2)). 문장 아래 관찰 줄은 선 없이 같은 대응을 보인다. |
| 문장 × 관찰 종류 행렬(표) | 칸 대부분이 비어 읽기 어렵고, 원문의 읽는 흐름이 깨진다. 역할이 정해지면 문장마다 볼 관찰은 한두 개다. |

## 5. 팀이 정할 것

1. **U1 범주에 "알아채고 밝히고 우회함"을 더할까.** 연습 E2 기록은 지시와 다른 파일을 고치고 마지막 보고에서 그 사실을 밝혔다. 지금 범주로는 (다) "말없이 우회"와 섞인다. 권장: 범주를 (다1) 밝히고 우회, (다2) 말없이 우회로 나눈다. 2.1의 F5가 그 구분을 보인다. 정답표 형식(M9-T3)의 `response` 값도 함께 바꾼다.
2. **문장 역할(N11)을 화면에 보일까, 관찰 줄을 고르는 데만 쓸까.** 권장: 작은 글자로 보인다. 역할이 틀렸을 때 사용자가 관찰 줄이 왜 그 줄인지 알 수 있다.
