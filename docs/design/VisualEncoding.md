# 시각화 인코딩 설계

이 문서는 [과업과 데이터 추상화](TaskAbstraction.md)의 정보 항목(D1\~D40)을 **어떤 시각 요소로 그리고 어떤 상호작용으로 다룰지** 정한다. 시각화 설계의 단계 중 "인코딩·상호작용"에 해당한다([중첩 모델과 과업 추상화](../research/VisualizationPrinciples.md#42-중첩-모델과-과업-추상화)). 요소마다 설계 근거와 검토한 대안을 함께 적는다. TVCG 기준이 이것을 요구한다([과제 수행에서 지킬 TVCG 기준](../research/TargetVenues.md#4-과제-수행에서-지킬-tvcg-기준)). 관련 작업은 이슈 I32다. 전체 문서 목록은 [문서 인덱스](../index.md)에서 확인한다.

이 문서는 화면의 설계안이다. 구현은 이 문서가 확정된 뒤 로드맵 태스크로 나눠 진행한다([7절](#7-구현-순서)). 지금 화면의 구성은 [웹 UI 설계](WebUI.md)와 [작업 흐름 그래프 설계](FlowGraph.md)에 있다.

## 1. 설계 원칙

[과업과 데이터 추상화의 설계 함의](TaskAbstraction.md#52-데이터-특성에서-나온-설계-함의)와 [시각화 원칙 조사의 설계 지침](../research/VisualizationPrinciples.md#6-agentvis-설계-지침)에서 다음 원칙을 정한다.

1. **세 층: 집계 → 선택 → 원본.** 기본 화면은 집계(어디를 볼지)다. 사용자가 기준 사건을 고르면 그 앞뒤를 보여 주고, 원본(전문, diff, 출력)은 누를 때만 연다. 잘 만든 로그 도구가 모두 이 구조다([관련 결과물 조사의 공통 구조](../research/RelatedWork.md#42-옮길-아이디어-상위-10개)).
2. **가로축은 기본이 실행 순서다.** 과업 T1·T4·T6의 판단은 "무엇이 무엇보다 먼저인가"다. 실제 시간 축에서는 긴 대기(사람 응답, 긴 테스트)가 축을 차지해 순서가 뭉개진다. 실제 시간은 T5(시간을 쓴 곳)를 위해 전환해서 본다. 시간을 압축했으면 그 사실을 표시한다([시각 채널의 효과 순위](../research/VisualizationPrinciples.md#45-시각-채널의-효과-순위)).
3. **강한 색은 실패에만 쓴다.** 실패는 3%의 드문 사건이다([전주의 속성과 주의](../research/VisualizationPrinciples.md#44-전주의-속성과-주의)). 실패는 빨강과 기호 ✕를 함께 쓴다([색과 접근성](../research/VisualizationPrinciples.md#49-색과-접근성)). 나머지 분류는 모양, 짧은 글자 표지, 위치로 나타낸다.
4. **수치는 공통 축 위의 위치·길이로 그린다.** 면적, 색 진하기, 원 크기로 수치를 나타내지 않는다(Cleveland & McGill).
5. **과업용 연결은 실행 구조 간선과 다른 층이다.** 실행 구조(띄움·돌아옴·병렬)는 지금의 흐름 그래프가 맡는다. 주장 ↔ 근거, 실패 → 다음 행동, 정정 ↔ 직전 행동 같은 **과업 연결**은 시간 순서를 지키는 호(arc)로 따로 그린다. AgentLens 같은 기존 연구와 갈라지는 지점이다([관련 결과물 조사의 기여 공간](../research/RelatedWork.md#34-agentvis의-기여-공간)).
6. **추정은 확정과 다르게 그린다.** 추정 값은 점선 테두리와 `추정` 표지를 붙이고, 누르면 판정 근거(원본 단계)로 간다. LLM 요약은 `요약` 표지를 붙이고 원문으로 가는 길을 둔다.
7. **텍스트는 한 줄 요약과 원문으로 나눈다.** 기본 화면의 텍스트는 한 줄(80자 안팎)이다. T6에서만 지시·계획 요약을 기준점 옆에 늘 보이게 둔다.

## 2. 화면 구성

```text
┌─ 세션 머리 ───────────────────────────────────────────────────────────────────┐
│ 제목 · 턴 12 · 도구 호출 318 · 실패 9      [순서 | 실제 시간]                 │
├─ E1 개요 띠(턴 시퀀스) ───────────────────────────────────────────────────────────┤
│        ◆                   ┆압축                    ◆                         │
│ [#1][#2 ✕2][#3][#4][#5][#6]┆[#7][#8 ✕1][#9][#10][#11 ✕6][#12]               │
├─ E3 이동 배지 ─────────────┬─ E2 신호 카드 ───────────────────────────────────┤
│ 실패 9 ◀ ▶  정정 3 ◀ ▶     │ ┆추정┆ 마지막 완료 주장 뒤 테스트 실행 없음  → │
│ 주장 2 ◀ ▶  압축 1 ◀ ▶     │ ┆추정┆ 실패 뒤 테스트 파일에 skip 추가        → │
│                            │ ┆추정┆ 같은 오류 ×4 (pytest AssertionError)   → │
├─ 과업 보기(탭) ────────────┴──────────────────────────────────────────────────┤
│ [기준 사건 E4] [문제 E5] [파일 E8] [서브에이전트 E9] [구간 E7]                │
│                                                                               │
│  (고른 보기. 턴 시퀀스에서 고른 턴을 보여 준다)                               │
├─ 원본 ────────────────────────────────────────────────────────────────────────┤
│ 고른 단계의 전문, 입력, 출력, diff (지금의 단계 목록과 흐름 그래프)           │
└───────────────────────────────────────────────────────────────────────────────┘
```

- 세 층에 맞춰 위에서 아래로 놓는다. 개요(E1\~E3) → 과업 보기(E4\~E10) → 원본.
- E11·E12(I57)는 새 보기가 아니다. 개요(턴 시퀀스·배지)와 원본 층(흐름 그래프 노드)에 기호와 칩을 얹고, 세션 수준의 목록을 하나씩 둔다.
- 모든 보기는 같은 선택 상태(고른 턴, 고른 기준 사건, 고른 단계)를 공유한다(조정된 다중 보기). 한 곳에서 고르면 나머지가 함께 바뀐다.
- 선택 상태는 지금처럼 URL 해시에 둔다([웹 UI 설계의 화면 구성](WebUI.md#2-화면-구성)).
- 지금의 턴별 단계 목록과 흐름 그래프는 원본 층으로 내린다. 지우지 않는다. 실행 구조를 볼 때(병렬, 서브에이전트의 실제 시간)는 여전히 흐름 그래프가 맞다.

## 3. 요소별 인코딩

요소마다 표현하는 정보 항목, 마크와 채널, 근거, 검토한 대안을 적는다. 마크는 점·선·막대·영역·글자, 채널은 위치·길이·모양·색·글자 표지다.

### 3.1 E1 개요 띠

개요 띠는 세션의 **턴 시퀀스**를 그린다(I37).

| 항목 | 내용 |
| --- | --- |
| 정보 | D1 턴(지시), D31 턴 순서, 턴의 실패 수(D14의 합), D2 작업 중 사용자 메시지, D35 압축, D21 턴의 걸린 시간 |
| 마크 | 턴마다 칸 하나. 칸 안에 `#순번`, 실패가 있으면 `✕개수`. 칸 위에 기호(노란 ◆ 작업 중 사용자 메시지, 흐름 그래프와 같은 모양). 압축은 칸 사이·칸 안을 가르는 점선 |
| 채널 | 가로 위치 = 턴 순서. 실패가 있는 턴만 빨강 + ✕, 나머지는 회색. 칸 너비는 기본이 같은 너비이고, 전환하면 걸린 시간에 비례 |
| 상호작용 | 칸을 누르면 그 턴을 고른다. 고른 턴은 파랑 테두리 |
| 과업 | 모든 과업의 입구. 어느 턴을 볼지 고른다. 턴 안의 기준 사건은 턴 상자(E4, 흐름 그래프)에서 본다 |

- **근거**
  - 세션 수준의 단위는 턴이다. 사용자는 턴 단위로 지시하고 결과를 받는다. 세션 상자는 턴을, 턴 상자는 단계를 보여 주면 상자마다 맡는 수준이 하나가 된다([웹 UI 설계의 책임 나누기](WebUI.md#2-화면-구성)).
  - 칸 하나가 지시 하나라서 칸의 뜻이 바로 읽힌다. 실패가 있는 턴은 턴 수의 일부라 빨강이 전주의적으로 보인다.
- **바꾼 이유**(2026-11-07, I37): 처음 안은 도구 호출마다 막대를 그린 띠였다. 사용자 검토에서 두 문제가 나왔다.
  - 막대 하나가 무엇을 뜻하는지 알 수 없었다. 수백 개의 1\~6px 막대에는 이름을 붙일 수 없다.
  - 턴 안의 활동은 아래 턴 상자(흐름 그래프, 단계 목록)가 이미 보여 준다. 같은 정보를 두 수준에서 되풀이했다.
- **대안 1: 도구 호출 띠**(처음 안, 위의 이유로 버림). 실패 단계로 바로 가는 기능은 이동 배지(E3)가 실패한 턴으로 가면서 그 턴의 첫 실패 단계를 고르는 방식으로 살린다.
- **대안 2: 턴별 sparkline 목록**([설계 지침 2](../research/VisualizationPrinciples.md#6-agentvis-설계-지침)). 턴마다 줄이 생겨 화면을 많이 차지하고, 턴 안의 활동을 다시 그리게 된다.
- **대안 3: 세션 전체 간트 차트**(AgentLens의 타임라인). 막대가 같은 무게로 그려져 어디를 볼지 알려 주지 못한다.
- **대안 4: 걸린 시간 비례를 기본으로.** 사람을 기다린 긴 턴이 띠를 차지해 짧은 턴은 칸이 너무 좁아진다. 전환으로만 둔다. 시간을 가장 많이 쓴 턴(T5)을 찾을 때 쓴다.

### 3.2 E2 신호 카드

| 항목 | 내용 |
| --- | --- |
| 정보 | 판정 규칙이 찾은 문제 후보. D7·D12·D24(T1), D25·D28·D36(T2), D29(T3), 규칙 위반·D35(T4), D18·D37(T5) |
| 마크 | 카드 한 줄: `표지 · 문장 · 횟수 · →` |
| 채널 | 글자와 숫자. 추정은 점선 테두리와 `추정` 표지 |
| 상호작용 | 누르면 그 후보가 기준 사건이 되고 E4가 열린다. 근거 단계가 원본 층에 펼쳐진다 |
| 과업 | T1, T2, T3, T4, T5의 입구 |

- **근거**: 세션을 열자마자 "어디부터 볼지"를 알려 주는 Datadog Watchdog Insights의 방식이다([옮길 아이디어 9](../research/RelatedWork.md#42-옮길-아이디어-상위-10개)). 실패 3%의 세션에서 탐색 시간을 줄인다.
- **위험**: 카드가 판정을 대신하면 참가자가 카드만 믿는다. 그래서 카드는 "후보"라고만 말하고, 정답 여부는 사용자가 근거를 보고 정한다. 유저 스터디에서는 카드를 끈 조건과 켠 조건을 비교할지 정해야 한다([8절](#8-확인할-것)).
- **대안: 카드 없이 E1·E3만.** 사용자가 직접 찾아야 해 T1(주장 뒤 검증 없음)처럼 "없는 것"을 찾는 과업에 약하다. 없는 것은 띠에 그려지지 않기 때문이다.

### 3.3 E3 이동 배지

| 항목 | 내용 |
| --- | --- |
| 정보 | 기준 사건이 있는 턴의 개수와 위치. 실패한 턴(D14), 작업 중 사용자 메시지가 있는 턴(D2), 대화 요약(문맥 압축)이 일어난 턴(D35). 완료 보고가 있는 턴(D7, E11)과 테스트 파일을 바꾼 턴(D25, E12)은 M8-T6에서 더한다 |
| 마크 | `실패한 턴 3 ◀ ▶` 같은 배지 |
| 상호작용 | ◀ ▶와 단축키로 다음·이전 턴으로 간다. 실패한 턴으로 가면 그 턴의 첫 실패 단계를 고른다. E1의 고른 턴과 턴 상자가 함께 움직인다 |
| 과업 | T4·T5·T6의 첫 위반, 첫 실패, 정정 지점 찾기 |

- **근거**: Honeycomb·lnav의 다음 오류로 가기([옮길 아이디어 1](../research/RelatedWork.md#42-옮길-아이디어-상위-10개)). 드문 사건을 스크롤 없이 돈다. 턴 단위로 이동하고 실패 단계를 함께 고르면, 세션 수준(어느 턴)과 턴 수준(어느 단계)의 답을 한 번에 준다.
- **대안: 상태로 걸러 보기만.** 걸러 내면 앞뒤 맥락이 사라진다. 이동은 맥락을 남긴 채 초점만 옮긴다.

### 3.4 E4 기준 사건 보기

이 요소가 AgentVis의 중심이다. 기준 사건 하나를 가운데 고정하고 앞뒤 단계를 세로로 늘어놓은 뒤, 과업 연결을 왼쪽 여백에 호로 그린다.

```text
     과업 연결   단계(실행 순서, 위 → 아래)                         표지
     ╭──────╮    ▪ Bash  pytest tests/ -q              ✓  종료 0    [테스트]
     │      │    ▪ Edit  src/app/cart.py  +12 −3                  [소스]
     │      │    ▪ Edit  src/app/cart.py  +1 −1                   [소스]
     │      ╰──▶ ⚑ 응답 "모든 테스트가 통과했습니다"              ┆추정: 완료 주장┆
     │            └ 근거: 마지막 테스트 실행 뒤 편집 2개 (실행 없음)
```

| 항목 | 내용 |
| --- | --- |
| 정보 | 기준 사건(D7 주장, D14 실패, D35 압축, D2 정정), 앞뒤 단계(D10·D11 한 줄, D14, D15), 과업 연결(주장 ↔ 근거 실행, D36 실패 → 다음 행동, D29 편집 ↔ 그 전 읽기, 정정 ↔ 직전 행동), 표지(D12 명령 종류, D25 파일 역할, D28 변경 표지, D13 명령 변형), 변경 내용(D27) |
| 마크 | 단계마다 한 줄. 과업 연결은 왼쪽 여백의 호. 표지는 오른쪽 끝의 짧은 글자 칩 |
| 채널 | 세로 위치 = 실행 순서. 기준 사건 줄은 굵은 테두리. 호의 모양: 실선은 확정 연결, 점선은 추정 연결. 실패만 빨강 + ✕ |
| 상호작용 | 앞뒤 단계 수 조절(기본 앞 15, 뒤 10). 반복 단계 접기(E6). 편집 줄은 펼치면 그 자리에 diff(D27)가 열린다. 줄을 누르면 원본 층에 전문 |
| 과업 | T1(주장 ↔ 근거), T2(실패 → 변경, 역할·표지 칩), T6(정정 ↔ 직전 행동, 지시 요약), T4(압축선 앞뒤) |

- **과업별 구성**
  - **T1**: 기준 사건은 ⚑ 완료 주장이다. ◆는 작업 중 사용자 메시지에 쓰므로 주장은 깃발로 구분한다(I39). 호는 주장에서 마지막 검증 실행으로 간다. 그 실행 뒤의 편집은 호 안쪽에 들어가므로 "근거 이후 변경"이 위치로 보인다. 출력 자르기(`| tail`)나 좁힌 실행(`-k`)은 실행 줄의 표지 칩으로 보인다.
  - **T2**: 기준 사건은 ✕ 테스트 실패다. 호는 실패에서 다음 변경으로 간다. 변경 줄의 칩이 `[테스트] skip 추가`이면 판단이 끝난다. 오른쪽 여백에 테스트 수(통과·실패·건너뜀)의 작은 계단 그래프를 둔다(E10).
  - **T4**: 기준 사건은 압축선이다. 앞뒤를 나란히(왼쪽 압축 전, 오른쪽 압축 후) 두고, 맨 위에 규칙 목록(D9)을 두고, 규칙별 위반 수를 압축 전후의 공통 축 막대 두 개로 비교한다. 압축 뒤 첫 위반 줄을 강조한다.
  - **T6**: 맨 위에 지시(D1)와 규칙(D9)의 요약을 고정한다. 기준 사건은 ◆ 작업 중 사용자 메시지(정정)이고, 호는 정정에서 직전 행동으로 간다. 에이전트의 계획(D6·D8)은 한 줄 요약으로 행동 줄 사이에 끼운다. 사용자가 "여기서부터 벗어남"을 표시할 수 있다([설계 지침 9](../research/VisualizationPrinciples.md#6-agentvis-설계-지침)).
- **근거**
  - 과업이 원하는 것은 전체 시간축이 아니라 기준 사건과 그 앞뒤다([설계 함의 1](TaskAbstraction.md#52-데이터-특성에서-나온-설계-함의)). 초점과 맥락(Furnas)을 단계 수로 구현한 형태다.
  - 과업 연결은 드물고(기준 사건마다 1\~3개) 방향이 있으며 시간 순서를 지켜야 한다. 한 줄로 늘어선 순서 위의 호(arc diagram)는 순서를 보존하면서 연결을 보여 준다.
- **대안 1: 흐름 그래프에 과업 연결 간선을 더한다.** 실행 구조 간선(띄움·돌아옴·병렬)과 섞여 둘 다 읽기 어려워진다. 흐름 그래프의 가로 배치는 실제 시간이라 "편집이 근거 뒤에 있다"는 판단도 거리로만 보인다.
- **대안 2: 힘 기반 노드-링크 그래프.** 순서가 사라진다. 우리 연결은 모두 "앞 → 뒤"이므로 순서가 판단의 절반이다.
- **대안 3: 인접 행렬.** 연결이 드물어 칸 대부분이 빈다. 순서도 읽기 어렵다.
- **대안 4: 판정 결과만 표로.** 근거(앞뒤 맥락)가 없어 사용자가 추정을 검증할 수 없다. 설계 원칙 6에 어긋난다.

### 3.8 E8 파일 행렬

```text
파일(폴더별)                 역할    읽음·편집 순서(실행 순서 축)           +/−
▾ src/app/
    cart.py                  소스    R···E··E··E                           ███ +40 −12
    price.py                 소스    ·······E                ⚠ 읽지 않음   █ +3 −1
▾ tests/
    test_cart.py             테스트  ···R·········E  skip 추가             ▏ +1 −0
```

| 항목 | 내용 |
| --- | --- |
| 정보 | D23 읽은 파일, D24 바꾼 파일, D29 편집 전 읽음, D25 역할, D26 바뀐 줄 수, D30 편집 왕복, D28 변경 표지 |
| 마크 | 파일마다 한 줄. 가운데는 E1과 같은 축 위의 작은 기호(R 읽기, E 편집). 오른쪽은 더함·지움 막대 |
| 채널 | 가로 위치 = 실행 순서. 바뀐 줄 수 = 막대 길이. 읽지 않고 편집은 ⚠ 기호와 글자. 역할은 글자 칩 |
| 상호작용 | 폴더 접기(경로 계층). 역할로 걸러 보기. 정렬: 경로, 바뀐 줄 수, 첫 편집 순서. 기호를 누르면 원본 층에 diff |
| 과업 | T3(무엇을 읽고 바꿨나, 읽지 않고 바꾼 파일), T2(실패 뒤 테스트 파일 변경) |

- **근거**: T3의 데이터는 파일 × 행동의 표(C+ × C)이고 파일 경로는 계층이다([T3 분석](TaskAbstraction.md#43-t3-무엇을-했는지-파악)). 행마다 작은 시간 띠를 두는 small multiples는 "편집이 읽기보다 앞섰다"와 "같은 파일을 여러 번 고쳤다"를 같은 축 위치로 보여 준다.
- **대안 1: 트리맵.** 파일 계층과 크기는 보이지만 순서(읽기 → 편집)가 사라지고, 면적으로 줄 수를 비교하게 된다.
- **대안 2: 파일 목록만.** 지금 경쟁 도구 대부분의 방식이다. "읽지 않고 편집"을 찾으려면 사용자가 순서를 머릿속에서 맞춰야 한다.

수업 실험의 T1(완료 보고 파악, I57)을 위한 요소다. 주장과 근거를 잇지 않고, 보고가 **무엇이고 어디 있는지**만 보인다.

```text
                [#1][#2][#3][#4 ✕1][#5][#6][#7][#8]
                실패한 턴 1 ◀ ▶   완료 보고가 있는 턴 4 ◀ ▶

                #4  ⚑ "pytest 12개 모두 통과합니다"       ┆추정┆
                #4  ☑ 할 일 "API 테스트 작성" 완료          확정
```

| 항목 | 내용 |
| --- | --- |
| 정보 | D7 완료 보고(문장 또는 할 일 항목, 턴, 응답 위치, 출처), D31 순서 |
| 마크 | 턴 시퀀스 칸 위의 ⚑ 기호. 흐름 그래프에서 보고가 든 응답 노드의 ⚑. 세션 수준의 목록(한 줄에 보고 하나) |
| 채널 | 위치 = 턴. 출처는 테두리로 구분한다. 응답 글에서 찾은 문장은 점선(추정), 할 일 도구의 완료 항목은 실선(확정)이다. 색은 쓰지 않는다(빨강은 실패 전용) |
| 상호작용 | E3에 `완료 보고가 있는 턴 ◀ ▶` 배지를 더한다. 목록의 줄을 누르면 그 턴과 그 응답 노드를 고른다 |
| 과업 | T1(수업 실험). 제출용 실험의 T1에서는 E4의 주장 ⚑가 이 표시에서 출발한다 |

- **규칙**(추정): 주 에이전트의 응답 글에서 완료 문장 사전("완료했습니다", "추가했습니다", "고쳤습니다", "모두 통과", "done", "fixed" 등)에 맞는 문장을 뽑는다. 할 일 도구의 `completed` 전환은 확정 보고로 더한다. 사전은 시나리오 세션의 정답 목록으로 재현율을 확인해 고친다.
- **근거**: 보고는 턴 마지막 응답의 48%에 있고 여러 턴에 흩어진다([실측](TaskAbstraction.md#41-t1-근거-없는-성공-보고)). 흩어진 드문 사건은 개요 위 기호 + 이동 배지로 찾게 하는 것이 E1·E3의 원칙과 같다. 답이 "목록"이므로 목록을 직접 준다.
- **대안 1: 응답 글 안에서 강조만.** 사용자가 턴을 하나씩 열어야 해 모으는 일이 그대로 남는다.
- **대안 2: LLM으로 보고를 요약해 목록화.** 문장이 바뀌면 사용자가 원문과 맞출 수 없다. 수업 실험은 원문 문장을 그대로 보이고, 요약은 제출용 실험에서 검토한다.

| 항목 | 내용 |
| --- | --- |
| 정보 | D12 테스트 실행, D14·D19 결과(통과·실패와 요약 수), D13 출력 자르기, D24·D25 테스트 파일 변경, D31 순서(변경 직전의 테스트 결과) |
| 마크 | 테스트 실행 노드에 ✓(통과)·✕(실패) 기호. 테스트 파일을 바꾼 Edit·Write 노드에 `[테스트]` 글자 칩. 출력 자르기는 `┆출력 자름┆` 칩. 세션 수준의 테스트 변경 목록 |
| 채널 | 실패는 지금처럼 빨강 + ✕. 테스트 실행의 통과는 색 없이 ✓. 실패 직후의 테스트 변경은 굵은 테두리로 강조한다. Bash로 쓴 것으로 추정한 변경은 점선이다 |
| 상호작용 | E3에 `테스트 파일을 바꾼 턴 ◀ ▶` 배지를 더한다. 목록의 줄을 누르면 그 변경 노드를 고른다 |
| 과업 | T2(수업 실험), T1 보조(마지막 테스트 실행과 그 결과) |

- **규칙**(추정): [T2 식별의 판정 규칙](TaskAbstraction.md#42-t2-테스트-변조건너뛰기)을 쓴다. 결과는 출력의 요약을 먼저 보고 종료 코드는 그다음이다. 실측에서 실패를 가린 실행이 92회 있었다.
- **근거**: 판단에 필요한 것은 두 종류 사건(실행, 변경)과 그 순서다. 흐름 그래프에 이미 순서가 있으므로 새 보기를 만들지 않고 노드에 분류를 얹는다. 범주가 둘(테스트인가 아닌가)이라 글자 칩 하나로 충분하다.
- **대안 1: 파일 행렬(E8) 전체.** 모든 파일을 줄로 두면 테스트 파일이 묻힌다. 수업 실험의 질문은 테스트 파일에 한정되므로 E8은 제출용 실험까지 미룬다.
- **대안 2: 변경 표지(skip 추가 등) 자동 표시.** 내용 판정으로 한 걸음 들어간다. 넣더라도 "글자가 들어 있음"을 보이는 표지일 뿐 변조 판정이 아니라는 점이 사용자에게 오해될 수 있어 수업 실험에서는 뺀다.

## 4. 데이터 유형별 인코딩 규칙

[2절의 데이터 유형](TaskAbstraction.md#2-데이터-유형)마다 쓰는 채널을 하나로 정해, 요소가 달라도 같은 정보는 같은 모양으로 보이게 한다.

| 유형 | 채널 | 쓰지 않는 채널 | 예 |
| --- | --- | --- | --- |
| Q 수치 | 공통 축 위의 길이·위치 | 면적, 색 진하기, 원 크기 | E5 횟수, E7 시간, E8 줄 수 |
| O 순서 | 위치(가로 또는 세로) | | 실행 순서, 턴 순번 |
| C 분류(적음) | 모양 기호, 글자 칩 | 색상(실패 말고는) | 기준 사건 기호, 파일 역할, 명령 종류 |
| C+ 분류(많음) | 줄(행)로 묶고 개수 막대 | 색상, 모양 | 오류 서명, 파일 경로 |
| B 이진 | 기호 있음·없음(⚠, ✕) | | 편집 전 읽음, 실패 |
| T 시간 | 위치(기본은 순서, 전환하면 실제 시간) | | 턴 시퀀스, 흐름 그래프 |
| X 비정형 텍스트 | 한 줄 요약 + 원문 펼침 | | 지시, 응답, 출력 |
| S 반정형 텍스트 | 원본 층에서 구문 강조(명령, diff) | | 명령, 오류, diff |
| G 연결 | 순서 축 위의 호(과업 연결), 노드-링크(실행 구조) | 힘 기반 배치 | E4 호, 흐름 그래프 |
| H 계층 | 들여쓰기·접기 | 트리맵 | 파일 경로, 서브에이전트 트리 |

**색 사용**: 실패(빨강 + ✕) 하나만 강한 색이다. 고른 턴·고른 단계는 파랑 테두리, 나머지는 회색 계열이다. 모든 색은 기호나 글자와 함께 쓴다.

**확정과 추정**: 확정은 실선, 추정은 점선과 `추정` 표지, LLM 요약은 `요약` 표지다. 세 가지가 모든 요소에서 같다.
