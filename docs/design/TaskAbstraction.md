# 과업과 데이터 추상화

이 문서는 AgentVis가 다룰 6가지 과업마다 사용자가 문제를 풀려고 **어떤 정보를 보고 싶어하는지** 분석한다. 그리고 그 정보가 **어떤 특성의 데이터인지**(수치, 분류, 시간, 텍스트, 연결 등) 분석한다. 시각화 설계의 단계 중 "데이터·과업 추상화"에 해당한다([중첩 모델과 과업 추상화](../research/VisualizationPrinciples.md#42-중첩-모델과-과업-추상화)). 인코딩(무엇을 어떤 시각 요소로 그릴지)은 이 문서를 입력으로 삼아 다음 단계에서 정한다. 관련 작업은 이슈 I31이다. 전체 문서 목록은 [문서 인덱스](../index.md)에서 확인한다.

과업의 출처는 [Claude Code 실무 고충 조사의 우선순위](../research/ClaudeCodePainPoints.md#4-시각화와-유저-스터디에-맞는-우선순위)이고, 데이터의 원천은 [데이터 소스](../DataSource.md)와 [분석기 설계](Analysis.md)다.

## 1. 방법

1. **과업 문장.** 과업마다 사용자가 답해야 할 질문을 한 문장으로 쓴다. 행동과 대상은 Brehmer & Munzner(2013)의 과업 분류로 적는다(찾기 locate, 확인 identify, 비교 compare, 요약 summarize, 조회 lookup).
2. **판정 절차.** 사용자가 원본 기록(Claude Code 화면이나 세션 기록)만으로 그 질문에 답한다면 거칠 단계를 적는다. 단계마다 필요한 정보가 곧 정보 요구다.
3. **정보 항목 사전.** 여러 과업에 같은 정보가 나오므로 항목을 한 번만 정의한다([3절](#3-정보-항목-사전)). 항목마다 다음을 적는다.
   - 원천 필드
   - 데이터 유형([2절](#2-데이터-유형))
   - 원본인지 파생인지
   - 확정인지 추정인지([진단 신호의 구분](../ProductVision.md#3-진단-신호))
   - 규모
4. **우선도.** 과업마다 항목을 **필수**(없으면 답할 수 없음)와 **보조**(있으면 빨라지거나 확신이 커짐)로 나눈다.
5. **검증.** 이 목록은 연구자의 분석에서 나온 가설이다. 유저 스터디의 형성 단계(인터뷰, 파일럿)에서 참가자에게 실제로 무엇을 보는지 확인하고 고친다([유저 스터디 설계](../research/VisualizationPrinciples.md#71-평가-시나리오와-연구-구성)). 시각화 학회는 추상화가 사용자에게서 검증되었는지를 본다.

**규모의 기준**(2026-10-31, 이벤트 저장소의 세션 전체): 턴 191개, 단계 3,169개, 도구 호출 1,293개, 실패 표시 39개(3%), 작업 중 사용자 메시지 18개다. 한 세션의 도구 호출은 많게는 418개, 한 턴은 대개 수십 개다.

## 2. 데이터 유형

Munzner의 데이터 추상화를 따르되, 우리 데이터에서 실제로 나오는 형태로 나눈다.

| 기호 | 유형 | 뜻 | 예 |
| --- | --- | --- | --- |
| Q | 수치 | 크기와 차이에 의미가 있는 값. 연속값과 개수 | 실행 시간(ms), 바뀐 줄 수, 반복 횟수, 토큰 수 |
| O | 순서 | 순서만 의미가 있는 범주 | 심각도(정보 < 경고 < 오류), 턴 순번 |
| C | 분류 | 순서 없는 범주. 범주 수가 적으면 C, 많으면 C+(예: 파일 경로, 오류 서명) | 도구 이름, 상태, 파일 역할, 규칙 ID |
| B | 이진 | 참·거짓 두 값의 분류 | 오류 여부, 편집 전 읽었는지 |
| T | 시간 | 시점, 또는 구간(시작·끝) | 호출 시각, 실행 구간, 문맥 압축 시점 |
| X | 비정형 텍스트 | 사람이 읽어야 뜻이 나오는 글 | 사용자 지시, 모델 응답, 명령 출력 |
| S | 반정형 텍스트 | 문법이 있어 파싱하면 구조가 나오는 글 | 셸 명령, 오류 메시지, diff |
| G | 연결 | 항목 사이의 관계. 트리(계층), 방향 그래프, 링크 | 서브에이전트 띄움 트리, 실패 → 다음 행동, 같은 파일의 편집 왕복 |
| H | 계층 | 트리 모양의 분류 | 파일 경로(폴더 구조), 프로젝트 → 세션 → 턴 → 단계 |

덧붙이는 구분이 두 가지 있다.
- **원본/파생**: 원본은 기록에 그대로 있는 값이고, 파생은 원본에서 계산한 값이다.
- **확정/추정**: 파생 값 가운데 규칙으로 판정하는 값이 추정이다(예: "이 명령은 테스트 실행이다"). 화면은 확정과 추정을 구분해 보여 줘야 한다([진단 신호](../ProductVision.md#3-진단-신호)).

## 4. 과업별 분석

각 과업의 정보 요구는 **필수**와 **보조**로 나눈다. ID는 [3절](#3-정보-항목-사전)의 항목이다.

### 4.1 T1 근거 없는 성공 보고

- **과업**: "에이전트가 마지막에 말한 '완료·통과'는 실제 실행 결과로 뒷받침되는가?"
- **행동·대상**: 주장을 찾고(locate), 근거 실행과 비교한다(compare).
- **판정 절차**
  1. 마지막 응답에서 완료·통과 주장을 찾는다.
  2. 그 주장이 기대는 검증(테스트, 빌드)을 찾는다.
  3. 주장 직전의 마지막 검증 실행과 그 결과를 본다.
  4. 그 실행 뒤에 코드가 또 바뀌었는지 본다.
  5. 그 실행이 결과를 가리지 않았는지 본다. 출력을 잘라 종료 코드가 0이 되었는지, 일부 테스트만 돌렸는지다.

| 우선도 | 정보 |
| --- | --- |
| 필수 | D7 주장(종류와 위치), D12 테스트·빌드 실행, D15 종료 코드, D14 상태, D31 순서(주장 ↔ 마지막 검증 ↔ 이후 편집), D24 마지막 검증 뒤 바뀐 파일 |
| 보조 | D19 테스트 결과 수, D13 출력 자르기·좁힌 실행, D16 출력 앞부분, D25 바뀐 파일의 역할 |

- **데이터 특성**: 핵심은 **주장(C)과 근거 실행(C + T) 사이의 연결(링크)과 시간 순서**다. "주장 이후 편집 수(Q)"와 "근거의 신선도(마지막 검증 뒤 경과)"는 파생 수치다.
- **한계**: 주장 추출(D7)과 테스트 명령 분류(D12)는 추정이다. 실험 시나리오에서는 테스트 명령을 하나로 정해 추정 오류를 줄인다.

#### 수업 실험의 T1: 완료 보고 파악 (I57)

2026-11-09 사용자 결정: 위 판정("근거가 있나")은 주석자마다 정답이 갈리고, 화면도 판정 규칙(M8-T2) 없이는 돕지 못한다. 수업 실험에서는 판정의 앞 단계인 **식별**만 잰다. 무엇이 완료됐다고 보고됐는지 알면 사용자는 "이것을 다시 확인해"라고 지시할 수 있다. 판정은 제출용 실험(1.2)에서 다룬다([수업 이후 학회 제출 계획](../research/SubmissionPlan.md#4-실험-계획-수업-실험과-제출용-실험)).

- **과업**: "에이전트가 무엇을 완료했다고 보고했나? 그 보고는 어느 턴에 있나?"
- **행동·대상**: 주장을 찾아(locate) 목록으로 모은다(identify). 비교는 하지 않는다.
- **완료 보고의 정의**: 두 출처를 쓴다.
  - 할 일 도구(TodoWrite, Task 도구)에서 상태가 `completed`가 된 항목. 기록된 구조라 확정이다.
  - 응답 글의 완료 문장("완료했습니다", "고쳤습니다", "모두 통과", "done", "fixed" 등). 규칙으로 찾으므로 추정이다.
- **필수 정보**: D7 주장(문장, 위치, 출처), D31 순서(어느 턴의 몇 번째 응답인가). 보조: D1 그 턴의 지시.
- **정답**: 시나리오 세션마다 주석자가 완료 보고 목록을 만든다. 참가자 답을 재현율·정밀도와 걸린 시간으로 잰다.
- **실측**(2026-11-09, 로컬 DB의 세션 619턴):
  - 턴의 마지막 응답에 완료 문장이 있는 턴이 297개(48%)다. 그런 응답 하나에 평균 2.2개가 있다. 턴 중간 응답에도 106턴(17%)에 있다.
  - 할 일 도구의 완료 기록은 0건이다. 이 기록들에서는 할 일 도구를 쓰지 않았다. 시나리오 세션에서 쓰이는지는 자료를 만들 때 확인한다.
  - 따라서 주 출처는 응답 글이다. 보고가 여러 턴에 흩어져 있어, 턴이 많은 세션에서는 터미널로 다시 모으기 어렵다. 이것이 시각화가 도울 지점이다. 반대로 턴 1\~2개짜리 세션에서는 기준선과 차이가 없으므로 시나리오에 쓰지 않는다.

### 4.2 T2 테스트 변조·건너뛰기

- **과업**: "에이전트가 실패를 코드로 고쳤는가, 아니면 테스트를 바꾸거나 건너뛰었는가?"
- **행동·대상**: 실패 뒤 변경을 확인하고(identify), 변경의 성격을 분류한다.
- **판정 절차**
  1. 테스트 실패를 찾는다.
  2. 실패 뒤에 바뀐 파일과 그 역할(소스·테스트·설정)을 본다.
  3. 테스트·설정 파일의 변경 내용에서 건너뛰기, 단언 삭제, mock, 실행 대상 축소를 찾는다.
  4. 테스트 수가 줄었는지 본다.
  5. 최종 통과가 어느 변경 뒤에 왔는지 본다.

| 우선도 | 정보 |
| --- | --- |
| 필수 | D14·D12 테스트 실패, D24·D25 실패 뒤 바뀐 파일과 역할, D27 변경 내용, D28 변경 표지, D36 실패 → 다음 행동 |
| 보조 | D19 테스트 수의 변화(시간에 따른 수치 계열), D26 바뀐 줄 수, D13 좁힌 실행 |

- **데이터 특성**: **분류(파일 역할, 변경 표지)가 붙은 사건 열(T)**과, 실패에서 변경으로 가는 **링크(G)**가 핵심이다. 변경 내용(S)은 근거로 펼쳐 보는 상세다. 테스트 수의 변화는 **시간에 따른 수치 계열(Q × T)**이다.

#### 수업 실험의 T2: 테스트 변경 파악 (I57)

2026-11-09 사용자 결정: 테스트가 제대로 된 테스트인지, 허들을 낮춘 테스트인지 내용으로 판정하는 일은 너무 어렵다. 수업 실험에서는 **테스트가 언제 돌았고, 테스트 파일이 언제 바뀌었는지**를 찾게 한다. 화면은 "실패 → 테스트 파일 변경"이라는 사건의 순서만 보여 준다. 그 변경이 변조인지 정당한 수정인지는 사용자가 판단한다. 판정은 제출용 실험(1.2)에서 다룬다.

- **과업**: "에이전트가 바꾼 테스트 파일은 무엇이고 언제 바꿨나? 테스트 실패 직후에 테스트 파일을 바꾼 지점은 어디인가? 마지막 테스트 실행의 결과는?"
- **행동·대상**: 분류된 사건을 찾고(locate), 두 사건의 순서를 확인한다(identify). 변경 내용의 성격은 분류하지 않는다.
- **필수 정보**: D12 테스트 실행, D14·D19 그 결과(통과·실패), D24·D25 바뀐 파일과 역할(테스트인가), D31 순서. 보조: D13 출력 자르기, D27 변경 내용.
- **판정 규칙**(추정, 규칙은 [인코딩 설계 E12](VisualEncoding.md#312-e12-테스트-사건-표시)에 둔다)
  - 테스트 파일: 경로 규칙(`tests/`, `test_*.py`, `*_test.go`, `*.test.ts`, `*.spec.js`, `__tests__/` 등).
  - 테스트 실행: Bash 명령의 각 부분(`&&`, `;`, 줄바꿈으로 나눈 것)이 테스트 실행기로 시작하는지 본다(`pytest`, `python -m unittest`, `npm test`, `go test`, `cargo test` 등). heredoc 본문은 보지 않는다.
  - 결과: **출력을 먼저 본다**(`N failed`, `FAILED (`, `OK`, `N passed`). 출력에 요약이 없을 때만 종료 코드를 쓴다.
- **정답**: 위 사건은 기록에서 규칙으로 뽑고, 주석자는 시나리오 세션에서 규칙의 결과를 확인만 한다.
- **실측**(2026-11-09, 로컬 DB)
  - 테스트 실행 422회가 모두 출력을 파이프로 잘랐다(`| tail`, `| grep`). 그중 92회는 출력에 실패가 있는데 종료 코드가 0이었다. 표본 6개 중 5개가 실제 실패를 가린 경우였다. **종료 코드만으로 통과·실패를 정하면 틀린다.** 이 현상은 원래 T1의 "결과를 가린 실행"과 같은 것이라, 출력 자르기 표지(D13)는 수업 실험에서도 보인다.
  - Edit·Write로 테스트 파일을 바꾼 호출이 49개다. Bash(`cat > tests/...`, `sed -i`, 파이썬 heredoc)로 테스트 파일을 쓴 것으로 보이는 명령이 약 80개다. 명령 안의 경로 추출은 거칠어 이 수에는 잘못 잡힌 것이 섞여 있다. **Bash로 바꾼 파일은 추정으로만 잡힌다.**
  - 테스트 실패 직후 테스트 파일을 바꾼 지점은 약 24개다. 이 수는 Bash 추정을 포함한다.
- **한계**: 경로 규칙은 언어와 프로젝트마다 다르다. 실험 시나리오 저장소의 테스트 경로가 규칙에 맞는지 자료를 만들 때 확인한다. 시나리오에서는 에이전트가 테스트 파일을 Edit·Write로 바꾸게 해, 추정 사건이 정답에 들어가지 않게 한다.

### 4.3 T3 무엇을 했는지 파악

- **과업**: "에이전트가 어떤 파일을 읽고 바꿨는가? 읽지 않고 바꾼 파일이 있는가? 서브에이전트는 무엇을 했는가?"
- **행동·대상**: 전체를 요약하고(summarize), 특정 파일·서브에이전트를 조회한다(lookup).
- **판정 절차**
  1. 바뀐 파일 목록을 본다.
  2. 파일마다 그 전에 읽었는지 본다.
  3. 서브에이전트마다 맡은 일, 쓴 도구, 건드린 파일, 돌려준 결과를 본다.
  4. 병렬로 한 일이 무엇인지 본다.

| 우선도 | 정보 |
| --- | --- |
| 필수 | D24 바뀐 파일, D23 읽은 파일, D29 편집 전 읽음, D33 서브에이전트 트리와 일, D34 서브에이전트 결과 |
| 보조 | D26 파일별 바뀐 줄 수, D25 파일 역할, D32 병렬, D20 실행 구간, D10 도구 분포 |

- **데이터 특성**: **파일 × 행동(읽기·편집)의 표**(C+ × C, 칸은 B·Q)다. 파일 경로는 **계층(H)**이고, 서브에이전트는 **트리(H/G)**다. 사람이 읽어야 하는 서브에이전트 지시·결과(X)는 요약이 필요하다(LLM 요약 허용, I26).

### 4.4 T4 문맥 압축 전후 행동 변화

- **과업**: "문맥 압축 뒤 에이전트가 규칙을 잊었는가? 언제부터 어겼는가?"
- **행동·대상**: 압축 전과 후를 비교하고(compare), 첫 위반을 찾는다(locate).
- **판정 절차**
  1. 압축 시점을 찾는다.
  2. 규칙 목록을 본다.
  3. 압축 뒤 각 행동이 규칙을 어기는지 본다.
  4. 첫 위반을 찾는다.
  5. 압축 전과 비교한다. 위반 빈도, 이미 고친 실패의 재발, 이미 읽은 파일의 재읽기를 본다.

| 우선도 | 정보 |
| --- | --- |
| 필수 | D35 압축 시점, D9 규칙 목록, 규칙 위반 사건(D9 × D11·D24·D13, 파생 C + T), D31 순서 |
| 보조 | D2·D3 압축 뒤 사용자 정정, D37 압축 전 실패의 재발, D23 재읽기, 압축 전후 비율(Q) |

- **데이터 특성**: **시간축을 둘로 나누는 사건(T)**과, 그 앞뒤의 **분류 사건(규칙 위반, C)** 비교다. "압축 전후 위반 비율"은 두 구간의 수치 비교(Q)다.
- **한계**: 짧은 과업에서는 압축이 드물다(I26의 압축 문항 처리 결정이 필요하다).

### 4.5 T5 루프·반복 실패

- **과업**: "에이전트가 시간을 가장 많이 쓴 구간은 어디이고, 그 이유는 무엇인가? 같은 실패를 몇 번 되풀이했는가?"
- **행동·대상**: 가장 큰 구간을 찾고(locate, 극값), 반복을 요약한다(summarize).
- **판정 절차**
  1. 구간별 걸린 시간을 비교해 가장 긴 구간을 찾는다.
  2. 그 구간 안의 실패와 재시도를 본다.
  3. 같은 오류가 몇 번 났는지 본다.
  4. 시도 사이에 무엇이 달라졌는지 본다. 같은 수정의 반복인지, 다른 방법인지다.

| 우선도 | 정보 |
| --- | --- |
| 필수 | D21 실행 시간, D40 대기 시간, D38 구간 묶음, D18 오류 서명, D37 반복 횟수와 구간 |
| 보조 | D30 편집 왕복, D27 시도 사이의 변경 차이, D36 실패 → 다음 행동, D39 토큰 |

- **데이터 특성**: **구간(T)에 붙은 수치(Q)의 비교**(가장 긴 것 찾기)와, **같은 서명(C+)의 묶음과 횟수(Q)**다. 시도 사이의 차이는 **텍스트 비교(S)**라 상세에서 보여 준다.

### 4.6 T6 지시 위반 지점

- **과업**: "에이전트가 어느 지점부터 사용자의 지시(또는 규칙)에서 벗어났는가?"
- **행동·대상**: 지시와 행동을 비교하고(compare), 처음 벗어난 지점을 찾는다(locate).
- **판정 절차**
  1. 지시와 규칙을 읽는다.
  2. 에이전트의 계획(응답·생각)과 행동을 차례로 지시와 대조한다.
  3. 사용자가 정정하거나 중단한 지점을 단서로 그 직전을 본다.
  4. 처음 벗어난 단계를 정한다.

| 우선도 | 정보 |
| --- | --- |
| 필수 | D1 지시, D9 규칙, D2·D4 사용자 정정·중단(시점), D6·D8 계획(응답·생각), D11·D24 행동, D31 순서 |
| 보조 | D3 메시지 성격, D5 권한 거부, 규칙 위반 사건(4.4), D36 실패 → 다음 행동 |

- **데이터 특성**: 핵심 근거가 **비정형 텍스트(지시, 계획)와 행동 사건열 사이의 대조**다. 자동 판정이 가장 어렵다(최고 방법도 14.2%, [시각화 원칙 조사](../research/VisualizationPrinciples.md#23-텍스트로그-조건과-비교한-실증-연구)). 그래서 화면은 판정을 대신하지 않고 대조를 돕는다. 지시와 정정을 시간축의 기준점으로 고정하고, 그 앞뒤 행동을 나란히 보여 준다.
- **정답**: 실험 시나리오에서는 기계적으로 확인할 수 있는 규칙(D9)을 넣어 정답을 만든다(I26).
- **지시가 틀린 경우**(2026-11-07, I51): [제품 비전의 Q6](../ProductVision.md#2-핵심-분석-질문)를 넓혀, 지시나 환경 설정 자체가 틀렸는데 에이전트가 따른 경우도 이 과업에 든다. 판정 절차의 2단계에 "지시가 저장소 사실과 맞는지"를, 3단계에 "환경 오류(D15 종료 코드, D17 오류 메시지)와 에이전트의 확인 질문이 있었는지"를 더한다. 정보 항목은 새로 필요하지 않고, D15·D17이 이 경우의 필수 항목이 된다. 실험에서 쓸지는 유저 스터디 설계(I26)에서 정한다([고충 조사 6.4절](../research/ClaudeCodePainPoints.md#64-유저-스터디에-주는-함의)).

### 5.2 데이터 특성에서 나온 설계 함의

인코딩은 다음 단계에서 정하지만, 데이터 특성이 이미 몇 가지를 정한다.

1. **모든 과업의 뼈대는 시간 순서(T)다.** 다만 과업마다 필요한 것은 전체 시간축이 아니다. **기준 사건**(주장, 실패, 압축, 사용자 정정)과 그 **앞뒤**가 필요하다. 그래서 기본 화면은 기준 사건을 고정하고 앞뒤를 펼치는 형태가 맞는다. 원칙의 근거는 [초점과 맥락](../research/VisualizationPrinciples.md#46-초점과-맥락fisheye)이다.
2. **핵심 판단은 대부분 "연결"(G)이다.** 연결의 예는 주장 ↔ 근거 실행, 실패 → 다음 행동, 편집 ↔ 그 전 읽기, 정정 ↔ 직전 행동이다. 지금 흐름 그래프의 간선은 실행 구조(띄움·돌아옴)만 잇는다. 과업용 연결은 따로 만들어야 한다.
3. **분류(C)는 강조와 걸러 보기에 쓴다.** 상태, 파일 역할, 변경 표지, 명령 변형, 규칙 위반이 여기에 해당한다. 범주가 많은 분류(C+: 파일 경로, 오류 서명)는 색으로 구분할 수 없다. 묶음과 개수(목록, 막대)로 보여 준다.
4. **수치(Q)는 비교·극값 과업(T5)과 요약에만 필수다.** 실행 시간, 반복 횟수, 바뀐 줄 수, 테스트 수가 여기에 해당한다. 나머지 과업에서는 보조다.
5. **텍스트(X, S)는 근거로 펼쳐 보는 상세다.** 단, T6에서는 텍스트 대조 자체가 과업이다. 지시와 계획을 짧게 요약해(LLM 요약 허용) 기준점 옆에 둔다.
6. **추정 값은 확정과 구분해 표시한다.** 주장 추출, 명령 분류, 변경 표지, 메시지 성격, 구간 묶음이 추정이다. 사용자가 근거(원본)로 바로 내려갈 수 있어야 한다.
