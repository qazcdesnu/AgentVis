# 과업과 데이터 추상화 2: 사용자 지시 오류

이 문서는 [연구 설계 2](../research/StudyDesign.md)의 세 과업(U1 대응 파악, U2 지시 오류 진단, U3 교정 결정)마다 사용자가 **어떤 정보를 보아야 답할 수 있는지**, 그 정보가 **기록의 어디에서 오고 어떤 특성의 데이터인지**를 정한다. 2.0.0 화면 설계([M10](../Roadmap.md#m10-지시-오류-중심-화면-200))의 입력이다. 방법과 데이터 유형 기호, 정보 항목 D1\~D40은 처음 설계의 [과업과 데이터 추상화](TaskAbstraction.md)를 그대로 쓰고, 이 설계에서 새로 필요한 항목만 N1\~N10으로 더한다. 관련 작업은 M9-T1이다. 전체 문서 목록은 [문서 인덱스](../index.md)에서 확인한다.

## 1. 전제: 실험 자료의 모양

- **세션 하나 = 시행 하나.** 참가자가 보는 기록은 한 과제의 실행 기록이다. 첫 사용자 입력이 과제 지시(이슈 글과 짧은 요청)이고, 사람은 그 뒤에 끼어들지 않는다. 기록은 [실행 기록 생성 도구](../Roadmap.md#m9-연구-설계-2의-실험-자료)(M9-T2)가 `claude -p`로 만든다.
- **에이전트는 사람에게 실제로 물을 수 없다.** 비대화형 실행이라 "묻기"는 질문으로 끝나는 응답(또는 질문 도구 호출)으로 기록에 남고, 그 뒤 실행이 끝난다. U1의 "알아채고 물음"은 이 흔적으로 정한다.
- **규모.** 과제 하나의 기록은 도구 호출 20\~80개를 목표로 한다([연구 설계 2의 원본 과제](../research/StudyDesign.md#41-원본-과제)). 처음 설계의 기록(세션당 수백 개)보다 작고, 턴은 대개 하나다. 따라서 이 설계의 화면은 "긴 세션의 개요"보다 **한 턴 안에서 지시와 행동을 대조하는 일**이 중심이다.

## 2. 과업별 분석

방법은 처음 설계의 [1절](TaskAbstraction.md#1-방법)과 같다. 과업 문장, 원본 기록만으로 답할 때의 절차, 필요한 정보, 우선도(필수·보조)를 적는다.

### 2.1 U1 대응 파악

- **과업**: "에이전트는 지시의 문제를 알아챘나? 알아챘다면 어느 단계에서, 어떻게 대응했나?"
- **행동·대상**: 해석이 드러난 지점을 찾고(locate), 대응의 종류를 확인한다(identify).
- **판정 절차**(원본 기록만으로)
  1. 지시가 가리킨 대상(파일, 함수, 재현 방법)을 읽어 둔다.
  2. 에이전트의 응답 글에서 지시를 다시 말하거나 지시와 다르게 말하는 문장을 찾는다("이슈에서는 …라고 했지만 실제로는 …").
  3. 에이전트가 지시에 없던 파일을 읽거나 고친 지점을 찾는다.
  4. 마지막 응답이 질문인지, 지시대로 했다고 보고하는지, 다른 방법을 썼다고 보고하는지 본다.
  5. 위 흔적 가운데 가장 이른 것을 "처음 알아챈 단계"로 고른다.

| 우선도 | 정보 |
| --- | --- |
| 필수 | N3 해석 문장, N4 사용자에게 한 질문, N5 지시 밖의 작업 위치, D31 실행 순서, D6 마지막 응답 |
| 보조 | N2 지시가 가리킨 대상, D23·D24 읽고 바꾼 파일, D8 생각(남아 있을 때) |

- **데이터 특성**: 해석 문장(X)과 질문(B + X)이 **시간 순서 위의 드문 사건(T)**으로 흩어져 있다. 답은 "그런 사건이 있었나(B), 처음은 언제(T), 마지막에 어떻게 했나(C)"다.

### 2.2 U2 지시 오류 진단

- **과업**: "처음 지시에서 잘못된 곳은 어디이고, 어떤 잘못인가? 잘못이 없다면 없다고 답한다."
- **행동·대상**: 지시의 문장과 기록의 증거를 대조하고(compare), 잘못된 문장과 유형을 확인한다(identify).
- **판정 절차**
  1. 지시를 문장 단위로 읽는다.
  2. 재현 시도(테스트나 재현 스크립트 실행)의 결과가 지시가 말한 증상과 같은지 본다. 다르면 E1(재현 조건 누락·왜곡)을 의심한다.
  3. 지시가 지목한 위치를 고친 뒤에도 실패가 남았는지, 에이전트가 다른 위치에서 원인을 찾았는지 본다. 그렇다면 E2(원인·위치 오도)를 의심한다.
  4. 한 요구를 맞추자 다른 테스트가 깨졌는지, 에이전트가 두 요구 중 하나를 골랐다고 말하는지 본다. 그렇다면 E3(모순된 요구)을 의심한다.
  5. 어느 것도 없으면 "잘못 없음"이다.

| 우선도 | 정보 |
| --- | --- |
| 필수 | N1 지시 문장, N2 지시가 가리킨 대상, N6 재현 시도와 결과, N7 지목 위치 수정 뒤 남은 실패, N8 충돌하는 테스트 결과 |
| 보조 | N3 해석 문장(에이전트가 이미 의심을 말했으면 빨라진다), D16·D17 출력과 오류, D27 변경 내용 |

- **데이터 특성**: 지시 문장(X, 순서 있는 목록)과 **증거 사건(C + T)** 사이의 **연결(G)**이 핵심이다. 증거는 지시의 특정 문장(대상)을 가리킬 때 가장 쓸모가 있다. 예: "`parse_date`를 고치라(문장 3)" ↔ "`parse_date`를 고친 뒤에도 `test_tz` 실패".

### 2.3 U3 교정 결정

- **과업**: "지금 에이전트에게 무엇을 지시하겠는가?"
- **행동·대상**: U1·U2의 결과를 바탕으로 개입을 고른다(decide). 시각화는 근거를 모아 줄 뿐이다.
- **판정 절차**
  1. U2로 잘못된 문장과 유형을 정한다.
  2. U1로 에이전트가 이미 무엇을 했는지(어디를 고쳤는지) 본다.
  3. 잘못된 전제를 바로잡고, 잘못 들어간 변경을 되돌리게 하고, 원래 요구는 지키는 지시를 고른다.

| 우선도 | 정보 |
| --- | --- |
| 필수 | U2의 필수 정보, D24·D27 지금까지 바꾼 파일과 내용 |
| 보조 | N3 해석 문장, D6 마지막 응답 |

- **데이터 특성**: 새 항목은 없다. U1·U2의 정보와 "지금까지 바뀐 것"의 목록(C+ + S)이다.

- **확정과 추정을 화면에서 가른다.** N2\~N8은 모두 규칙으로 찾는 추정이다. 화면은 추정임을 표시하고, 근거(원문 문장, 출력 줄)로 바로 갈 수 있게 한다. 도구는 "지시가 틀렸다"고 판정하지 않는다([연구 설계 2의 R5](../research/StudyDesign.md#7-화면-설계에-주는-요구)).
- **N2가 기반이다.** N5·N7은 N2가 대상을 잘 뽑아야 맞는다. 실험 과제의 지시는 연구자가 쓰므로, 지시에 파일·함수 이름을 백틱으로 적는 관례를 자료 만들기 지침에 넣는다(M9-T5).

### 4.2 설계 함의

1. **지시가 화면의 축이다.** U2·U3의 필수 정보가 모두 지시 문장(N1)에 연결된다. 지시를 늘 보이게 하고, 증거(N6\~N8)와 해석(N3)이 지시의 어느 문장을 가리키는지 연결로 보여야 한다.
2. **드문 사건을 앞으로 낸다.** U1의 답은 해석 문장, 질문, 지시 밖 작업이라는 드문 사건이다. 정상 작업(N9)을 접어야 이 사건들이 보인다.
3. **증거는 사건의 짝이다.** N7(편집 → 실패), N8(테스트 쌍)은 두 사건의 관계다. 사건 하나만 보여서는 뜻이 나오지 않으므로 짝을 함께 보인다.
4. **처음 설계의 기능 가운데 남길 것.** 흐름 그래프(실행 순서와 병렬), 테스트 사건 표지(M8-T6의 통과·실패), 단계 상세는 그대로 쓸 수 있다. 세션 개요 띠와 완료 보고 목록은 한 턴짜리 기록에서는 쓸모가 적다. 상세는 M10-T1에서 정한다.

### 4.3 검증

- 이 목록은 연구자의 분석에서 나온 가설이다. 수업 실험의 형성 확인([연구 설계 2의 6절](../research/StudyDesign.md#6-수업-실험파일럿에서-할-것))에서 참가자가 실제로 무엇을 보고 답하는지 확인하고 고친다.
- 판정 규칙(N2\~N8)의 정확도는 정답표(N10)로 잰다. 시행마다 정답 오류 유형의 증거 항목(E1 → N6, E2 → N7, E3 → N8)이 하나 이상 잡혔는지, 통제 시행에서 잘못 잡힌 것이 없는지 본다.
