# 작업 흐름 그래프 설계

이 문서는 턴 하나의 실제 실행 구조(병렬 도구 호출, 서브에이전트, 백그라운드 작업)를 시간 위의 그래프로 보여 주는 기능을 설계한다. 그래프의 재료는 [분석기 설계](Analysis.md)의 세션 모델이고, 근거가 되는 기록 구조는 [데이터 소스의 병렬 실행과 백그라운드 작업](../DataSource.md#35-병렬-실행과-백그라운드-작업의-연결)에 있다. 화면 기술과 보안 규칙은 [웹 UI 설계](WebUI.md)를 따른다. 관련 작업은 이슈 I24와 [로드맵](../Roadmap.md#m4-실시간-웹-ui)의 M4-T6~M4-T8이다. 전체 문서 목록은 [문서 인덱스](../index.md)에서 확인한다.

구현할 심볼은 인라인 코드로 적었다. 태스크를 시작할 때 [작업 관리 규칙](../TaskRule.md#41-시작)에 따라 코드 포인터 링크로 바꾼다. 3~5절은 M4-T7에서 바꿨다([graph 모듈](../../src/agentvis/analysis/graph.py)).

## 1. 목적

[웹 UI 설계의 턴과 단계 표시](WebUI.md#3-턴과-단계-표시)는 단계를 기록 순서대로 위에서 아래로 늘어놓는다. 이 방식으로는 동시에 일어난 일이 한 줄로 보인다. 예를 들어 테스트를 백그라운드로 돌리는 동안 서브에이전트 셋이 병렬로 일하고 그중 하나가 실패한 상황이 드러나지 않는다. 그래프는 이것을 보여 준다.

- 어느 줄(주 에이전트, 서브에이전트, 백그라운드 작업)에서 실패했는가 ([Q1, Q2](../ProductVision.md#2-핵심-분석-질문))
- 무엇이 동시에 실행되었고, 어디서 갈라지고 합쳐졌는가 ([Q3](../ProductVision.md#2-핵심-분석-질문))
- 실패 뒤 흐름이 어떻게 이어졌는가(재시도, 다른 방법). 반복 실패·fallback 판정(M5)의 결과를 나중에 이 그래프 위에 표시한다.
- 작업 도중 사람이 끼어든 지점이 흐름의 어디인가 ([Q6](../ProductVision.md#2-핵심-분석-질문))

## 2. `parentUuid`를 그대로 쓰지 않는 이유

세션 기록의 `parentUuid`는 기록이 쓰인 순서의 사슬이다([실측](../DataSource.md#35-병렬-실행과-백그라운드-작업의-연결)).

- 병렬로 낸 도구 호출이 한 줄로 이어진다.
- 갈라짐은 대부분 hook 첨부 기록이나 도구 결과 같은 곁가지다.
- 서브에이전트는 다른 파일에 있다.
- 백그라운드 작업의 끝은 나중의 작업 알림에만 나온다.

따라서 그래프는 아래 사실을 합쳐 만든다. `parentUuid`는 지금처럼 턴 귀속([분석기 설계의 턴](Analysis.md#3-턴))에만 쓴다.

| 그래프 구조 | 근거 |
| --- | --- |
| 갈라짐 | 같은 모델 응답(`message.id`) 안의 여러 도구 호출 |
| 합류 | 그 도구 호출들 다음의 모델 응답 |
| 서브에이전트 줄 | 띄운 도구 호출의 결과 `toolUseResult.agentId`와 서브에이전트 기록 |
| 백그라운드 줄 | `input.run_in_background`가 참인 호출부터, `<tool-use-id>`가 그 호출인 작업 알림까지 |
| 실행 구간 | hook의 `PreToolUse`부터 `PostToolUse`·`PostToolUseFailure`까지. hook이 없으면 세션 기록 시각 |

## 3. 그래프 모델

그래프의 단위는 **턴 하나**다. 턴 단위면 노드 수가 화면에서 읽을 만하고(이 세션의 턴당 도구 호출은 대부분 수십 개), 턴은 사람이 준 지시 하나의 수행 과정이라 분석 질문과도 맞는다. 세션 전체 그래프는 [7. 나중에 정할 것](#7-나중에-정할-것)에 둔다.

[build_turn_graph](../../src/agentvis/analysis/graph.py#build_turn_graph)`(session: SessionView, index: int) -> FlowGraph | None`이 [분석기](Analysis.md)가 만든 세션 모델에서 그래프를 계산한다. 원시 이벤트를 다시 읽지 않는 순수 함수이며, 모듈은 [graph 모듈](../../src/agentvis/analysis/graph.py)이다. 턴이 없으면 `None`이다.

### 3.1 줄

줄(lane)은 함께 순서대로 일하는 실행 주체 하나다.

| `kind` | 내용 | 시작 | 끝 |
| --- | --- | --- | --- |
| `main` | 턴의 주 에이전트 | 턴 시작 | 턴 끝과 이 줄 노드의 마지막 시각 중 늦은 것(백그라운드 줄은 넣지 않는다). 턴이 `running`이면 `None` |
| `subagent` | 동기 서브에이전트(`Agent` 호출의 결과가 서브에이전트가 끝난 뒤 옴) | 띄운 호출의 시작 | 띄운 호출의 끝 |
| `background_agent` | 백그라운드 서브에이전트 | 띄운 호출의 시작 | 그 호출의 작업 알림. 없으면 열린 채 |
| `background_shell` | 백그라운드 셸 명령 | 띄운 호출의 시작 | 그 호출의 작업 알림. 없으면 열린 채 |

줄은 [Lane](../../src/agentvis/analysis/graph.py#Lane)으로 나타내며, 필드는 다음과 같다.

| 필드 | 값 |
| --- | --- |
| `id` | `main`, 또는 띄운 도구 호출의 `tool_use_id` |
| `kind` | 위 표 |
| `label` | `main`은 "주 에이전트". 서브에이전트는 띄운 호출의 `input.description`(없으면 `subagent_type`). 셸은 `input.description`(없으면 `command` 첫 줄) |
| `parent` | 띄운 호출이 있는 줄의 `id`. `main`은 `None` |
| `spawned_by` | 띄운 도구 호출 노드의 `id`. `main`은 `None` |
| `started_at`, `ended_at` | 위 표. 끝을 모르면 `None` |
| `status` | `success`, `error`, `interrupted`, `running`, `unfinished`. 아래 규칙으로 정한다. |

`status`를 정하는 규칙:
- 서브에이전트 줄은 띄운 호출의 상태를 그대로 쓴다.
- 백그라운드 줄은 작업 알림의 `status`로 정한다. `completed`는 `success`, `failed`는 `error`, `killed`는 `interrupted`이고, 그 밖의 값은 `unfinished`다.
- 작업 알림이 없으면 세션이 진행 중일 때 `running`, 아니면 `unfinished`다.

띄운 도구 호출과 연결되지 않은 서브에이전트([분석기의 `subagent` 단계](Analysis.md#6-서브에이전트))도 `subagent` 줄이 된다. 줄 `id`는 `agent:<agent_id>`이고 `spawned_by`는 `None`이며, 상태는 턴이 `running`이면 `running`, 아니면 `unfinished`다. 서브에이전트가 다시 띄운 서브에이전트·백그라운드 작업도 같은 규칙으로 줄이 되며, `parent`가 그 서브에이전트 줄이다. 줄은 `main`을 첫째로 하고, 나머지는 시작 시각 순서다.

### 3.2 노드

| `kind` | 원천 단계([분석기의 단계](Analysis.md#4-단계)) | 모양 |
| --- | --- | --- |
| `prompt` | 턴 시작 지시. `main` 줄에만 있다. | 점 |
| `model` | 같은 `message_id`를 가진 `thinking`·`text` 단계 묶음. 응답 하나에 생각·글이 없으면 만들지 않는다. | 점 |
| `tool_call` | `tool_call` 단계 | 실행 구간 막대 |
| `background_task` | 백그라운드 셸 명령의 실행. 그 줄의 유일한 노드다. | 실행 구간 막대 |
| `user_message` | `user_message` 단계 | 강조 표시 |
| `notification` | `notification` 단계 | 점 |
| `compact`, `hook_failure` | 같은 이름의 단계 | 점 |

노드는 [Node](../../src/agentvis/analysis/graph.py#Node)로 나타내며, 필드는 다음과 같다.

| 필드 | 값 |
| --- | --- |
| `id` | 문자열. 원천 단계의 `id`다. 원천 단계가 하나가 아닌 노드는 다르게 붙인다. `prompt`는 `prompt`, `model`은 묶음 첫 단계의 `id`, `background_task`는 `bg:<tool_use_id>`다. |
| `lane` | 줄 `id` |
| `kind` | 위 표 |
| `started_at`, `ended_at` | 막대 노드는 실행 구간이다(아래). 점 노드는 둘 다 단계 시각이다. 끝나지 않은 막대는 `ended_at`이 `None`이다. |
| `label` | 짧은 이름. 도구 호출은 도구 이름과 입력 요약이고, 그 밖의 노드는 텍스트 첫 줄이다. |
| `status` | `tool_call`과 `background_task`만 가진다. [도구 호출 상태](Analysis.md#5-도구-호출)와 같다. |
| `step_ids` | 상세 보기를 위한 원천 단계 `id` 목록. 화면은 세션 상세의 단계를 이 `id`로 찾아 보여 준다. |

**막대 노드의 실행 구간**은 아래처럼 정한다.
- 시작은 `PreToolUse` hook 시각이다. hook이 없으면 `tool_use` 기록 시각이다.
- 끝은 `PostToolUse`·`PostToolUseFailure` hook 시각이다. hook이 없으면 도구 결과 기록 시각이다.
- `tool_use` 기록 시각은 실행 시작이 아니라 생성 시각이다([실측](../DataSource.md#35-병렬-실행과-백그라운드-작업의-연결)). 그래서 hook이 없는 구간의 막대는 실제보다 일찍 시작한다. 이 노드에는 `approximate: true`를 단다.

**`background_task`의 구간**은 띄운 호출의 시작부터 작업 알림 시각까지다.

### 3.3 간선

| `kind` | 의미 | 그리는 방법 |
| --- | --- | --- |
| `next` | 같은 줄 안의 다음 실행 | 실선 |
| `spawn` | 도구 호출이 줄을 띄움: 띄운 호출 → 자식 줄의 첫 노드 | 점선 |
| `return` | 자식 줄의 결과가 돌아옴. 동기 서브에이전트는 줄의 마지막 노드들 → 띄운 호출의 끝으로 간다. 백그라운드 줄은 마지막 노드 → 부모 줄의 작업 알림 노드로 간다. | 점선, 화살표 |

간선은 [Edge](../../src/agentvis/analysis/graph.py#Edge)로 나타내며, 필드는 `source`, `target`(노드 `id`), `kind`다. 양 끝 노드가 그래프에 없는 간선(작업 알림이 다른 턴에 있는 백그라운드 줄 등)은 넣지 않는다. 같은 간선은 한 번만 넣는다.

**`next` 간선 규칙**은 줄 하나의 노드를 시각 순서로 묶어 적용한다.
- 묶음은 둘 중 하나다.
  - 모델 응답 하나: 연달아 놓인, `message_id`가 같은 `thinking`·`text`·`tool_call` 단계. 묶음의 `model` 노드와 도구 호출 노드들이다.
  - 그 밖의 노드 하나. `message_id`가 없는 도구 호출(세션 기록이 아직 없어 hook으로만 만든 단계)도 여기에 든다.
- 직전 묶음의 끝 노드 집합을 **전선**(frontier)이라 한다. `main` 줄의 첫 전선은 `{prompt}`이다. 자식 줄의 첫 전선은 비어 있으며, 첫 노드는 `spawn` 간선으로만 들어온다.
- 모델 응답 묶음은 이렇게 잇는다.
  - `model` 노드 M이 있으면 전선의 각 노드 → M, 그리고 M → 각 도구 호출 노드로 잇는다(갈라짐).
  - M이 없으면 전선의 각 노드 → 각 도구 호출 노드로 잇는다.
  - 새 전선은 도구 호출 노드 전부다. 도구 호출이 없으면 `{M}`이다. 다음 묶음이 이 전선 전부에서 이어지므로 합류가 된다.
- 그 밖의 노드 N은 전선의 각 노드 → N으로 잇고, 새 전선은 `{N}`이다.

백그라운드 작업을 띄운 호출은 결과가 바로 오므로, 보통의 도구 호출처럼 전선에 들어가 다음 응답으로 이어진다. 백그라운드 작업 자체의 흐름은 그 줄과 `return` 간선이 보여 준다.

### 3.4 그래프

[FlowGraph](../../src/agentvis/analysis/graph.py#FlowGraph)는 다음 필드를 가진다.
- `session_id`
- `turn_index`
- `started_at`, `ended_at`: `main` 줄의 값. 턴이 멈춘 뒤 백그라운드 작업 알림을 받아 같은 턴으로 이어서 일하면 그 기록도 이 턴에 속하므로, 턴의 `Stop` 시각보다 늦은 노드가 있을 수 있다.
- `lanes`, `nodes`, `edges`: 3.1~3.3절

노드는 시작 시각 순서다.

## 4. 분석기 보강

그래프에는 원래 세션 모델에 없던 사실이 필요해, M4-T7에서 [분석기 설계](Analysis.md)에 아래 필드를 더했다(그 문서의 해당 표에 "M4-T7"로 표시했다). 같은 작업에서 서브에이전트 안의 hook 이벤트를 그 서브에이전트에 합치도록 고쳤다([분석기의 서브에이전트](Analysis.md#6-서브에이전트), H3).

- 단계의 `message_id`: `assistant` 기록의 `message.id`. 같은 응답의 블록을 묶는다.
- 도구 호출의 `started_at`, `ended_at`: 3.2절의 실행 구간 규칙.
- 도구 호출의 `background`: 백그라운드 실행이면 다음 필드를 가진 사전이고, 아니면 `None`이다.
  - `kind`: `shell` 또는 `agent`
  - `task_id`: `toolUseResult.backgroundTaskId`. 백그라운드 서브에이전트는 `agentId`다.
  - `status`, `ended_at`, `notification_step_id`: 연결된 작업 알림에서 가져온다. 알림이 아직 없으면 `None`이다.
- `notification` 단계의 `detail`에 `<task-notification>` 본문에서 읽은 `task_id`, `tool_use_id`, `status`를 더한다.

## 5. 조회 API

| 경로 | 응답 |
| --- | --- |
| `GET /api/sessions/{session_id}/turns/{index}/graph` | 3.4절의 그래프. 세션이나 턴이 없으면 `404`다. |

- [get_turn_graph](../../src/agentvis/analysis/catalog.py#get_turn_graph)`(store, session_id, index) -> FlowGraph | None`은 [분석기 설계의 조회 API](Analysis.md#8-조회-api)의 catalog 모듈에 있다. 이 함수는 그 문서의 `get_session`으로 세션을 만든 뒤 그래프를 계산한다. 경로는 [서버 앱](../../src/agentvis/server.py#create_app)에 있다.
- 응답 형식, 시각 표기, 동기 경로 함수, `Host` 검사는 [분석기 설계의 조회 API](Analysis.md#8-조회-api)와 같다.
- 노드의 상세 내용(입력 전체, 결과, 오류)은 그래프 응답에 다시 넣지 않는다. 화면이 이미 받은 세션 상세에서 `step_ids`로 찾는다.

### 6.1 배치

```text
 시간 →            ┆⋯ 2분 ┆
 주 에이전트   ●──●─┬─[Agent: 문서 리뷰 ✓]────────┬─●──●─[Bash ✕]─●──★────●
                    ├─[Agent: 코드 리뷰 ✓]──────┐ │                 사용자 메시지
                    └─[Bash 테스트 (bg) ✓]─┐    │ │
 서브: 문서 리뷰     ┆●─[Read]─[Grep]─●──────┼────┼─┘
 서브: 코드 리뷰     ┆●─[Read]─[Read ✕]─[Read]┼───┘
 백그라운드: 테스트  ┆[══════ uv run … ═══════]┘
```

- **세로**: 줄마다 띠 하나를 둔다. 줄 이름은 왼쪽에 고정한다. 자식 줄은 부모 줄 바로 아래에 둔다.
- **줄 안의 겹침**: 한 줄 안에서 화면상 겹치는 노드(동시에 실행된 도구 호출 등)는 줄 안의 하위 행에 나눠 놓는다. 앞에서부터 들어갈 수 있는 첫 행에 넣는다.
- **가로(시간)**: 실제 시간을 그대로 쓰면 몇 ms 차이의 호출이 겹치고, 사람을 기다린 몇 분이 화면 대부분을 차지한다. 그래서 순서를 지키는 압축 시간축을 쓴다.
  - 모든 노드의 시작·끝 시각을 정렬한다.
  - 이웃한 두 시각 사이의 화면 거리를 `clamp(실제 간격 × 비율, 최소 간격, 최대 간격)`으로 정하고, D3의 구간별 선형 척도(`d3.scaleLinear`에 여러 점의 정의역·치역)로 만든다.
  - 이 척도는 단조 증가라, 두 구간이 화면에서 겹치는 것과 실제로 겹친 것이 같다. 동시 실행 여부는 그대로 보존된다.
  - 최대 간격으로 줄어든 구간에는 끊김 표시와 실제 길이(예: "⋯ 2분")를 단다.
- **간선**: `d3.linkHorizontal` 곡선으로 그린다. 출발점은 출발 노드의 끝, 도착점은 도착 노드의 시작이다. 단, 동기 서브에이전트의 `return` 간선은 띄운 호출 막대의 끝으로 간다.
- **색과 기호**: 상태 색과 기호는 [웹 UI 설계](WebUI.md#3-턴과-단계-표시)와 같다. `user_message` 노드는 강조 배경색이며, 모든 줄을 가로지르는 세로 안내선을 긋는다. 사람이 끼어든 시점에 각 줄이 무엇을 하고 있었는지 보이게 하기 위해서다.

### 6.2 상호작용

- **확대·이동**: `Ctrl`(macOS는 `⌘`)+휠, 트랙패드 핀치, 또는 그래프 위의 `+`·`−`·`맞춤` 단추로 가로 배율을 바꾼다. 그냥 휠은 페이지 세로 이동에 남겨 둔다. 이동은 그래프 영역의 가로 스크롤로 한다. 배율이 바뀌면 시간축과 하위 행 배치를 다시 계산해 다시 그린다.
- **노드에 마우스를 올리면** 노드 이름, 상태, 실제 시각(시작~끝), 실행 시간을 보여 준다(SVG `<title>`). 근사한 막대는 "시각 근사"를 덧붙인다.
- **노드를 누르면** 그래프 아래 상세 영역에 그 단계의 상세를 보여 준다. 상세는 목록 화면의 단계 표시를 그대로 다시 쓴다.
- **보기 전환**: 세션 상세에 "흐름 그래프 | 목록" 단추를 둔다. 기본은 흐름 그래프다. 그래프 보기에서는 턴 고르기 목록(순번, 지시 첫 줄, 실패 수)에서 턴을 고르면 그 턴의 그래프를 그린다. 처음에는 마지막 턴을 고른다. 선택한 보기와 턴은 URL 해시(`view=graph|list`, `turn=<index>`)에 둔다.

### 6.3 그리기 규칙과 상수

| 항목 | 규칙 |
| --- | --- |
| 줄 순서 | `main`부터 깊이 우선. 자식 줄은 부모 줄 바로 아래에 시작 시각 순으로 둔다. |
| 줄 이름 칸 | 왼쪽 180px. 줄 종류(주·서브·백그라운드)와 이름, 상태 기호를 쓴다. |
| 행 높이 | 줄 안 하위 행 하나가 26px. 줄 띠는 번갈아 옅은 배경색을 쓴다. |
| 시간축 | 1초를 40px로 보고, 이웃 시각 사이 거리를 6~120px로 자른다. 120px로 잘린 구간에 끊김 표시와 실제 길이를 단다. 길이 글자가 앞 글자와 56px 안으로 붙으면 글자는 빼고 선만 긋는다(마우스를 올리면 길이를 보여 준다). 배율은 이 거리 전체에 곱한다. |
| 막대 | 도구 호출·백그라운드 작업. 높이 14px, 최소 너비 6px, 색은 상태 색이다. 너비가 충분하면 막대 안에 이름을 쓴다. 끝나지 않은 막대(`ended_at`이 `None`)는 그래프 끝까지 그리고 오른쪽 끝을 점선으로 한다. 근사한 막대는 테두리를 점선으로 한다. |
| 점 | `prompt`는 큰 점, `model`은 회색 작은 점, `notification`은 속이 빈 점, `compact`·`hook_failure`는 작은 사각형이다. `user_message`는 강조색 마름모이고, 그래프 전체 높이의 세로 안내선을 긋는다. |
| 간선 | `next`는 옅은 실선, `spawn`은 점선, `return`은 점선과 화살표다. |
| 겹침 판정 | 노드의 화면상 범위(점은 지름, 막대는 너비)에 4px 여백을 두고 판정한다. |

화면 코드는 [웹 UI 설계의 파일 구성](WebUI.md#5-파일-구성)의 `graph.js`에 있다.

### 6.4 보안

- 노드 이름과 상세는 세션 기록의 신뢰할 수 없는 텍스트다. D3에서도 `.text()`만 쓰고 `.html()`은 쓰지 않는다([웹 UI 설계의 보안](WebUI.md#4-보안)).

## 7. 나중에 정할 것

- 세션 전체를 한 그래프로 보기. 턴이 많은 세션에서 읽을 수 있는 배치가 필요하다.
- 긴 자식 줄 접기.
- 반복 실패·fallback·정정(M5) 표시.
- 실시간 갱신(M4-T2 SSE)과 함께 실행 중 막대를 늘이기.

## 8. 테스트

- [분석기 설계의 테스트](Analysis.md#9-테스트)와 같은 방식으로, 실측 형태의 원시 이벤트로 세션을 만든 뒤 그래프를 확인한다. 테스트 파일은 [tests/test_graph.py](../../tests/test_graph.py)다. 확인할 것:
  - 병렬 호출의 갈라짐과 합류
  - 생각·글이 없는 응답(`model` 노드 없음)
  - 동기 서브에이전트 줄과 `spawn`·`return`
  - 백그라운드 셸 명령과 작업 알림 연결(`background_task` 구간, 상태)
  - 알림이 아직 없는 백그라운드 줄(열린 채, `running`)
  - 백그라운드 서브에이전트 줄
  - 중첩 서브에이전트의 `parent`
  - hook이 없는 막대의 `approximate`
  - 턴 중간 `user_message`의 전선
- 조회 API는 `tests/test_api.py`에서 정상 응답과 `404`를 확인한다.
- 화면은 실제 서버를 띄워 브라우저로 확인한 결과를 완료 기록에 남긴다([웹 UI 설계의 테스트](WebUI.md#6-테스트)).
