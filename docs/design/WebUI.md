# 웹 UI 설계

이 문서는 AgentVis의 웹 화면(`src/agentvis/web/`)을 설계한다. 화면이 보여 주는 데이터는 [분석기 설계](Analysis.md)의 조회 API가 주고, 화면이 답해야 할 질문은 [제품 비전의 핵심 분석 질문](../ProductVision.md#2-핵심-분석-질문)에 있다. 관련 태스크는 [로드맵](../Roadmap.md#m4-실시간-웹-ui)의 M4-T2\~M4-T5다. 전체 문서 목록은 [문서 인덱스](../index.md)에서 확인한다.

2026-10-31 사용자 방침: "보면서 나중에 추가하고 고치면 된다." 이 문서는 첫 화면을 만들기 위한 권장안이며, 화면을 보고 고친다.

## 1. 기술과 라이브러리

| 항목 | 선택 | 이유 |
| --- | --- | --- |
| 화면 기술 | 빌드 단계 없는 HTML·CSS·JavaScript(ES 모듈) | [시스템 구조의 기술 선택](../Architecture.md#6-기술-선택)대로 도구 체인을 늘리지 않는다. |
| 시각화 라이브러리 | 첫 화면(목록)은 쓰지 않는다. [작업 흐름 그래프](FlowGraph.md)는 **D3**를 쓴다. | 목록은 CSS 세로 타임라인으로 충분하다. 그래프는 시간축 척도, 확대·이동, 곡선 간선이 필요하고, D3는 이를 세밀하게 제어할 수 있는 표준 도구다. 라이브러리는 [1.1절](#11-저장소에-넣은-라이브러리)대로 저장소에 넣어 쓴다. |
| 제공 방식 | 서버 앱이 `web/` 폴더를 정적 파일로 제공한다. `GET /`는 `index.html`이다. 응답마다 다시 확인하라는 캐시 지시를 붙인다([수집기 설계](Collector.md#2-http-엔드포인트), H5). | 별도 웹 서버 없이 `agentvis serve` 하나로 쓴다. 고친 화면 파일이 새로고침만으로 반영되어야 팀원이 예전 화면을 보지 않는다. |
| 갱신 | 서버가 보내는 변경 알림(SSE)을 받아 보고 있는 세션을 다시 그린다([8절](#8-실시간-갱신), M4-T2). "새로고침" 버튼은 모두 다시 받는다. | 진행 중인 세션을 옆에 띄워 두고 볼 수 있어야 현장 과업(유저 스터디)에 쓸 수 있다. |

### 1.1 저장소에 넣은 라이브러리

화면이 쓰는 외부 라이브러리는 **외부 CDN에서 받지 않고, 파일을 저장소의 `src/agentvis/web/vendor/`에 넣어 우리 서버가 제공한다.** CDN(Content Delivery Network)은 남이 운영하는 파일 배포 서버로, 화면을 열 때마다 브라우저가 그곳에서 라이브러리를 받아 온다. 2026-10-31에 사용자와 이 결정을 다시 검토했고(I24), 아래 이유로 유지한다.

| 기준 | 외부 CDN | 저장소에 넣기 |
| --- | --- | --- |
| 보안 | 화면에는 로컬 작업 기록 전체(명령, 파일 내용, 경로)가 올라온다. CDN의 파일이 바뀌거나 오염되면 그 스크립트가 이 내용을 읽어 밖으로 보낼 수 있다. 무결성 해시(SRI)로 줄일 수는 있다. | 저장소에 커밋해 검토한 파일만 실행된다. |
| 오프라인 | 인터넷이 없으면 화면이 깨진다. | 항상 동작한다. |
| 재현성 | 같은 주소의 내용이 바뀔 수 있다. | 커밋한 버전 그대로다. |
| 비용 | 없음 | 파일 하나(수백 KB)를 저장소에 두고, 판올림을 직접 한다. |

**넣는 절차**
1. 공식 배포처(npm 레지스트리의 패키지 압축 파일)에서 정확한 버전을 받는다. 받은 압축 파일을 레지스트리가 공개한 무결성 값(`dist.integrity`, SHA-512)과 대조한다.
2. 화면이 쓰는 배포 파일(예: `dist/d3.min.js`)과 라이선스 파일만 `vendor/`에 `<이름>-<버전>.<확장자>`, `LICENSE-<이름>.txt`로 둔다. 파일 내용은 고치지 않는다. git이 줄바꿈을 바꾸지 않도록 `.gitattributes`에서 `vendor/`를 `-text`로 둔다([운영체제 이식성](../CodeRule.md#31-운영체제-이식성)).
3. 아래 표에 파일, 버전, 라이선스, 출처, SHA-256을 적는다. 판올림할 때도 같은 절차를 밟고 표를 고친다.
4. `index.html`에서 `app.js`보다 먼저 일반 `<script>`로 불러온다. D3의 배포 파일은 전역 변수 `d3`를 만든다.

**넣은 라이브러리**

| 파일 | 라이브러리 | 버전 | 라이선스 | 출처 | SHA-256 |
| --- | --- | --- | --- | --- | --- |
| [d3-7.9.0.min.js](../../src/agentvis/web/vendor/d3-7.9.0.min.js) | D3 | 7.9.0 | ISC ([LICENSE-d3.txt](../../src/agentvis/web/vendor/LICENSE-d3.txt)) | npm `d3@7.9.0` `dist/d3.min.js` | `f2094bbf6141b359722c4fe454eb6c4b0f0e42cc10cc7af921fc158fceb86539` |

2026-10-31 M4-T8: `https://registry.npmjs.org/d3/-/d3-7.9.0.tgz`의 SHA-512가 레지스트리의 `dist.integrity`와 같음을 확인했다.

[웹 정적 파일 검사기](../VerificationTools.md#10-웹-정적-파일-검사기)가 이 절의 규칙 중 기계적으로 확인할 수 있는 부분을 검사한다.
- `vendor/`의 모든 파일이 이 표에 있고, 그 SHA-256이 표와 같은가
- 우리가 쓴 화면 파일에 외부 주소가 없는가

## 2. 화면 구성

세 영역을 가로로 놓는다. 화면이 좁으면 위아래로 쌓는다.

```text
┌──────────────┬──────────────────────┬───────────────────────────────────────────────┐
│ 프로젝트     │ 세션                 │ 세션 상세                         [새로고침]  │
│              │                      │ 일단 먼저 우리는 문서 규칙부터…  턴 51 · 실패 15 │
│ ▸ AgentVis   │ ▸ 일단 먼저 우리는…  │ ───────────────────────────────────────────── │
│   ~/Desktop/ │   10-31 04:41        │ ▾ #2 코드 작업 규칙 문서도 만들어라…  ✕2  ended │
│   세션 1     │   턴 51 · 실패 15    │   ◦ 생각 (접힘)                                │
│ ▸ ProjInit   │                      │   ▪ Write docs/CodeRule.md            ✓       │
│ ▸ AI윤리     │                      │   ▪ Bash python3 -m tools.check_docs  ✕ 오류   │
│   …          │                      │   ★ 사용자: 파이썬은 무조건 uv 환경에서 써라. │
│              │                      │   ▪ Bash uv init …                    ✓       │
│              │                      │ ▸ #3 …                                         │
└──────────────┴──────────────────────┴───────────────────────────────────────────────┘
```

- **프로젝트**(`GET /api/projects`): 이름, 상위 경로, 세션 수, 마지막 활동. 폴더가 없는 프로젝트는 흐리게 표시한다. 목록에 없는 폴더의 경로 직접 입력은 M4-T5에서 더한다.
- **세션**(`GET /api/sessions?project=…`): 제목, 마지막 활동, 턴 수, 도구 호출 수, 실패 수(0보다 크면 강조). 제목은 [분석기의 세션 제목](Analysis.md#7-세션)이고 두 줄까지 보이며, 넘치면 마우스를 올려 전체를 본다. 진행 요약이 있으면 마우스 설명에 함께 보인다(I47).
- **세션 상세**(`GET /api/sessions/{id}`): 아래 네 상자. 턴은 한 번에 하나를 고르며, 처음에는 마지막 턴을 고른다.
- **세션 상세의 상자**(I36): 세션 상세는 서로 다른 정보를 보여 주는 네 부분으로 이루어지며, 각 부분을 테두리와 배경이 있는 상자로 묶고 상자 왼쪽 위에 작은 제목을 단다. 위에서 아래로 놓는다.

  | 순서 | 상자 제목 | 내용 | 범위 |
  | --- | --- | --- | --- |
  | 1 | 세션 정보 | 제목, 진행 요약, 정보 줄(아래) | 세션 |
  | 2 | 세션 전체 흐름 | [개요 띠와 이동 배지](#7-세션-개요-띠와-이동-배지) | 세션 |
  | 3 | 턴 선택 | 턴 고르기 상자(순번, 지시 첫 줄, 실패 수), 고른 턴의 정보(시작 시각, 상태, 도구 호출 수, 실패 수), 여러 줄 지시의 전문(접힘) | 턴 |
  | 3.5 | 지시 대조 | 고른 턴의 지시(문장 번호, 지시가 가리킨 대상)와 규칙으로 찾은 신호 목록. 2.0.0에서 더했다([지시 대조 보기 설계](ReviewView.md#2-배치)). 2.0.0부터 목록 보기는 정상 단계 3개 이상의 연속을 한 줄 `정상 작업 n단계 · 걸린 시간`으로 접고(고른 단계가 그 안에 있으면 편다), 턴이 하나인 세션의 세션 전체 흐름 상자는 접어 둔다 | 턴 |
  | 4 | `턴 #n 작업 흐름` | 제목 줄 오른쪽의 `흐름 그래프 \| 목록` 단추, 고른 턴의 [작업 흐름 그래프](FlowGraph.md#6-화면)와 노드 상세, 또는 고른 턴의 단계 목록([3절](#3-턴과-단계-표시)) | 턴 |

  **세션 정보 상자**(I47):
  - 제목: [분석기의 세션 제목](Analysis.md#7-세션). 제목을 Claude Code가 지었으면(`title_source`가 `ai`) 마우스 설명에 "Claude Code가 지은 제목"을 적는다.
  - 진행 요약: `요약` 표지 + `recap.text` + `· Claude Code · 14:20`(`recap.at`). Claude Code가 생성한 글이라 확정 사실과 구분해 표지를 붙인다([인코딩 설계 원칙 6](VisualEncoding.md#1-설계-원칙)). 실시간 갱신으로 새 요약이 오면 바뀐다. 없으면 이 줄을 두지 않는다.
  - 정보 줄: 상태(`진행 중`: 마지막 턴이 실행 중, `대기 중`: 턴이 끝나 다음 지시를 기다림, `끝남`: `SessionEnd`), 시작 시각 \~ 마지막 활동 시각과 걸린 시간, 프로젝트, Git 브랜치, 턴·도구·실패 수.

  세션 범위 상자(1, 2)와 턴 범위 상자(3, 4)는 간격을 더 벌려 두 묶음으로 보이게 한다.

  **책임 나누기**: 상자마다 맡는 일이 하나다. 3번 상자는 **어떤 턴을 볼지**만 정하고, 두 보기에서 똑같다. `흐름 그래프 | 목록` 단추는 **고른 턴의 작업 흐름을 어떤 방식으로 그릴지**만 정하므로 그 흐름을 그리는 4번 상자의 제목 줄에 둔다. 단추를 바꿔도 고른 턴과 고른 단계는 그대로다(I36, 2026-11-07 사용자 지시).
- **사이드바 접기**(I35): 프로젝트·세션 영역의 제목 줄에 접기 단추(`◂`)를 둔다. 누르면 그 영역이 32px 너비의 세로 띠로 접히고, 띠에는 펴기 단추(`▸`)와 세로 글자 제목만 남는다. 두 영역은 따로 접는다. 세션 상세가 남은 폭을 모두 쓴다. 단추의 `aria-expanded`가 접힘 상태를 나타낸다. 접힘 상태는 보는 사람의 화면 취향이라 해시가 아닌 브라우저 저장소(`localStorage`)에 두고, 저장소를 쓸 수 없으면 펼친 상태로 시작한다. 좁은 화면(위아래로 쌓는 배치)에서는 접으면 목록만 숨기고 제목 줄은 남긴다.
- 선택 상태(프로젝트, 세션)는 URL의 해시(`#project=…&session=…`)에 둔다. 새로고침하거나 주소를 공유해도 같은 화면이 열린다.
- 세션 상세에는 이 문서의 목록 보기와 함께 턴별 [작업 흐름 그래프](FlowGraph.md#6-화면) 보기를 둔다(M4-T8).

## 3. 턴과 단계 표시

**턴 정보**: 순번, 사람이 입력한 지시(첫 줄, 여러 줄이면 펼쳐서 전체), 상태(`running`·`ended`·`failed`), 도구 호출 수, 실패 수, 시작 시각. 턴 선택 상자에 둔다([2절](#2-화면-구성)). 지시가 슬래시 명령이면 세션 제목과 같이 `/start`처럼 정리해 보인다(턴 고르기 상자, 턴 칸 설명, I47).

**단계**: [분석기 설계의 단계 종류](Analysis.md#4-단계)마다 표시를 정한다. 단계는 시간순 세로 타임라인이며, 색과 기호로 종류와 상태를 구분한다.

| 단계 | 표시 |
| --- | --- |
| `thinking` | 흐린 글씨, 기본은 접힘(첫 줄만). 펼치면 전문. 걸린 시간과 토큰이 있으면 `생각 4.2초 · 254토큰`처럼 앞에 적는다. 내용이 비었으면 펼칠 수 없는 한 줄로 `(내용이 기록에 남지 않음)`을 붙인다(I33). |
| `text` | 모델 응답. 기본 글씨. 길면 일부만 보이고 펼친다. 턴의 완료 보고가 든 글이면 앞에 `⚑ 완료 보고(응답 글에서 추정)`와 뽑은 문장을 적는다(M8-T6). |
| `tool_call` | 도구 이름 + 입력 요약(Bash는 `command`, 파일 도구는 `file_path`, 그 밖은 입력 JSON 앞부분) + 상태 기호. 펼치면 입력 전체, 결과, 오류, 실행 시간, 권한 요청 여부. 서브에이전트가 있으면 그 단계들을 들여써서 펼친다. 테스트 실행이면 제목 줄에 `테스트 통과`·`테스트 실패`·`테스트 결과 모름` 꼬리표를 달고, 펼치면 `테스트 결과: 실패 (2 failed, 68 passed) · 출력 요약으로 판정`과, 출력을 잘랐으면 `출력을 파이프로 잘라 종료 코드로는 결과를 알 수 없음`을 적는다. 테스트 파일 변경이면 `[테스트] 파일 변경` 꼬리표와 `테스트 파일: 경로 · 직전 테스트: 실패(요약) · Bash 명령에서 추정`을 적는다. 할 일 도구의 완료 보고면 `⚑ 완료 보고(할 일)`를 단다(M8-T6, [분석기의 테스트 사건과 완료 보고](Analysis.md#51-테스트-사건과-완료-보고)). 입력·결과·오류가 JSON이면 원문과 정리 보기를 바꾸는 두 단추를 둔다(아래, I43). |

**JSON 원문·정리 보기**(I43): 입력·결과·오류 칸의 제목 줄 오른쪽에 GitHub의 보기 전환처럼 나란한 두 단추 `[ 원문 | JSON 정리 ]`를 두고, 지금 보기를 눌린 모양으로 표시한다. 정리 보기의 들여쓰기는 4칸이다. 2칸은 너무 빽빽해 읽기 어렵다(I45, 사용자 지시).

| 칸 | 단추를 두는 조건 | 원문 | JSON 정리 | 기본 |
| --- | --- | --- | --- | --- |
| 결과, 오류 | 글 전체(앞뒤 공백 제외)가 `JSON.parse`로 해석된다 | 저장된 글 그대로 | 해석한 값을 들여쓰기 4칸으로 | 원문 |
| 입력 | 늘 (입력은 기록에서 이미 JSON 값이다) | 한 줄 JSON(`JSON.stringify(input)`) | 들여쓰기 4칸. 값 안의 문자열이 그 자체로 JSON이면 풀어서 함께 정리한다 | JSON 정리(지금까지의 모습) |

- `{`·`[`로 시작해도 해석되지 않으면(Read의 `[image]`, TOML, JSON 뒤에 다른 출력이 이어진 글) 단추를 두지 않는다. 2026-11-07 실측: 결과·오류 5,900건 중 해석되는 JSON은 96건, 해석되지 않는 `{`·`[` 시작 글은 617건이었다.
- 결과·오류가 잘렸고 `{`·`[`로 시작하는데 해석되지 않으면 잘린 JSON으로 보고, JSON 단추 대신 `잘린 JSON이라 정리할 수 없음 · 전체 보기로 받으면 정리할 수 있음`을 적는다(실측 26건).

**잘린 결과의 전체 보기**(I44): 결과·오류는 앞 2,000자만 받는다([결과 미리보기 길이](Analysis.md#5-도구-호출)). 응답의 `result_chars`·`error_chars`가 받은 글보다 길면 칸이 잘린 것이다.

- 잘린 칸의 제목 옆에 `전체 16,381자 중 앞 2,000자`를 적고 `전체 보기` 단추를 둔다.
- `전체 보기`를 누르면 확인 대화상자를 띄운다: `전체 길이는 16,381자입니다. 정말 전체 내용을 보시겠습니까?`와 `예`·`아니오` 단추. 브라우저 기본 창(`confirm`)은 단추가 "확인·취소"로 나와 쓰지 않고, `<dialog>` 요소로 만든다. 처음 초점은 `아니오`에 둔다. `Esc`나 바깥을 누르면 아니오와 같다.
- **예**: [전체 결과 API](Analysis.md#8-조회-api)로 그 도구 호출의 전체를 받아 칸을 바꿔 그린다. 받은 전체는 도구 호출마다 기억해, 실시간 갱신으로 다시 그려도 전체가 남는다. 전체가 JSON이면 JSON 단추가 생긴다. 받는 동안 단추에 `받는 중…`을 적고, 실패하면 칸 아래에 오류를 적는다.
- **아니오**: 대화상자만 닫는다. 칸, 스크롤, 고른 노드, 실시간 따라가기 상태 등 화면은 그대로다.
- 고른 보기는 **칸 종류마다 하나**(입력, 결과·오류)로 기억한다(I46). 한 칸에서 고르면 화면에 보이는 같은 종류의 칸이 모두 바뀌고, 다른 노드를 열거나 실시간 갱신·새로고침을 해도 그 보기로 나온다. 처음 만든 안은 칸마다 따로 기억해, 결과에서 정리 보기를 골라도 다른 노드를 열면 원문으로 돌아갔다(사용자 보고). 이 선택은 보는 사람의 취향이라 해시가 아닌 브라우저 저장소(`localStorage`)에 두고, 저장소를 쓸 수 없으면 기본 보기로 시작한다.
| `user_message` | 이름은 **작업 중 사용자 메시지**다. **강하게 강조**(눈에 띄는 배경). 작업 도중 사람이 보낸 메시지로, 지시 오해(Q6)를 볼 때 가장 중요한 지점이다. |

**사람이 보낸 두 메시지**(I39): 둘 다 사람이 보냈지만 기록과 역할이 다르므로 나눠 부른다([과업과 데이터 추상화의 D1·D2](TaskAbstraction.md#31-지시와-대화)).

| 이름 | 원천 | 역할 | 표시 |
| --- | --- | --- | --- |
| 턴 시작 지시 | 턴을 시작하는 사람 입력 `user` 기록(`promptId`). 턴마다 하나, 맨 앞 | 무엇을 하라고 했는가 | 노란 원 |
| 작업 중 사용자 메시지 | 진행 중인 턴에 전달된 `queued_command` 첨부. 턴 안에 0개 이상 | 끼어들어 정정·추가 지시를 한 지점 | 노란 마름모(◆), 흐름 그래프에서는 모든 줄을 가로지르는 세로 점선 |

사람이 보낸 것은 같은 노란색 계열(`--user-message-line`)로 묶고 모양으로 둘을 가른다. 시스템이 보낸 알림은 회색으로 둔다. 화면의 모든 곳(목록, 노드 상세, 턴 선택, 개요 띠, 그래프, 범례)에서 이 이름과 모양을 쓴다.
| `notification` | 흐린 한 줄(출처: 작업 알림, 하위 에이전트 보고, 사용자 셸 명령). 펼치면 전문. |
| `hook_failure` | 이름은 **실시간 신호 누락**이다. 빠진 hook 종류(`detail.hook_event`)에 따라 무엇을 세션 기록으로 보완했고 무엇을 잃었는지 한 줄로 적고, 원인을 덧붙인다(아래 표, I40). 보완된 것은 흐린 한 줄, 확인할 수 없는 것이 있으면 경고 색 한 줄이다. 펼치면 원래 오류 문구를 보여 준다. |

**빠진 hook의 안내**(I40, [실측](../DataSource.md#38-hook-전달-실패와-턴-끝-기록))

| 빠진 hook | 안내 | 정도 |
| --- | --- | --- |
| `PreToolUse`, `PostToolUse` | 도구 실행 시각을 세션 기록 시각으로 추정함 | 보완 |
| `PostToolUseFailure` | 실패 여부와 오류 문구를 세션 기록으로 보완함 | 보완 |
| `Stop` | 턴 끝을 세션 기록의 턴 소요 시간 기록으로 보완함 | 보완 |
| `UserPromptSubmit` | 턴 시작 지시를 세션 기록으로 보완함 | 보완 |
| `PermissionRequest` | 이 도구의 권한 요청 여부는 확인할 수 없음 | 잃음 |
| `SubagentStart`, `SubagentStop` | 서브에이전트의 정확한 시작·끝 시각은 확인할 수 없음 | 잃음 |
| `StopFailure` | 턴 실패의 오류 코드는 확인할 수 없음 | 잃음 |
| `Notification`, `SessionEnd`, 그 밖 | 이 신호의 내용은 확인할 수 없음 | 잃음 |

원인: 오류 문구에 `ECONNREFUSED`가 있으면 "AgentVis 서버가 꺼져 있었음"을, 그 밖에는 "전달 실패"를 적는다. 예: `실시간 신호 누락(Stop) · 턴 끝을 세션 기록의 턴 소요 시간 기록으로 보완함 · 원인: AgentVis 서버가 꺼져 있었음`.
| `compact` | 가로 구분선 "대화 요약(문맥 압축)". 대화가 길어져 Claude Code가 앞 대화를 요약문으로 바꾼 지점이다. 이 뒤로 에이전트는 앞의 세부 내용을 요약으로만 기억한다(I39). |
| `subagent` | 연결되지 않은 서브에이전트. 들여쓴 단계 묶음. |

## 4. 보안

- 세션 기록의 모든 텍스트는 신뢰할 수 없는 데이터다(다른 웹 페이지 내용, 명령 출력 등이 들어 있다). 화면에 넣을 때는 항상 `textContent`로 넣고 `innerHTML`을 쓰지 않는다. 저장된 텍스트가 스크립트로 실행되는 것(XSS)을 막기 위해서다.
- 화면은 같은 서버의 조회 API와 정적 파일만 `GET`으로 부른다. 예외는 실험 모드의 화면 사용 기록 전송(`POST /api/interactions`, [9절](#9-실험-모드))뿐이며, 같은 서버로만 보낸다. 외부 주소로 요청하지 않는다(외부 CDN, 글꼴 포함). 라이브러리는 [1.1절](#11-저장소에-넣은-라이브러리)대로 저장소에 넣어 쓴다.
- 모든 요청은 서버의 [요청 검증](Collector.md#21-요청-검증) `Host` 검사를 받는다. 화면은 `http://127.0.0.1:<포트>/` 또는 `http://localhost:<포트>/`로 연다.

## 6. 테스트

- [tests/test_api.py](../../tests/test_api.py)에서 `TestClient`로 `GET /`가 `index.html`을, `/app.js`·`/style.css`·`/graph.js`·`/overview.js`·`/review.js`·`/interaction.js`·저장소에 넣은 D3가 정적 파일을 돌려주고, 그 응답에 `Cache-Control: no-cache`가 있으며 같은 파일을 `If-None-Match`로 다시 물으면 `304`이고(H5), 조회 API 경로가 정적 파일 연결에 가려지지 않음을 확인한다.

## 7. 세션 개요 띠와 이동 배지

[시각화 인코딩 설계](VisualEncoding.md)의 E1 개요 띠와 E3 이동 배지를 세션 전체 흐름 상자에 둔다(M8-T1). 개요 띠는 세션의 **턴 시퀀스**다(I37). 인코딩의 근거와 버린 안(도구 호출마다 막대를 그린 띠)은 그 문서의 [E1](VisualEncoding.md#31-e1-개요-띠)과 [E3](VisualEncoding.md#33-e3-이동-배지)에 있다. 이 절은 구현 규칙을 정한다. 코드는 [src/agentvis/web/overview.js](../../src/agentvis/web/overview.js)다.

### 7.1 턴 요약

세션 상세 응답(`GET /api/sessions/{id}`)의 턴들에서 화면이 직접 계산한다. 새 API는 만들지 않는다. 턴마다 다음 값을 만든다.

| 값 | 계산 |
| --- | --- |
| 순번, 지시 첫 줄, 상태, 도구 호출 수, 실패 수 | 턴의 `index`, `prompt`, `state`, `tool_call_count`, `failure_count` |
| 실패 턴인지 | 실패 수가 0보다 크거나 상태가 `failed` |
| 첫 실패 단계 | 주 에이전트 단계 중 상태가 `error`·`interrupted`인 첫 도구 호출의 `id` |
| 작업 중 사용자 메시지 수 | `user_message` 단계 수 |
| 압축 수 | `compact` 단계 수 |
| 걸린 시간 | `ended_at`(없으면 마지막 단계의 `at`) − `started_at` |
| 완료 보고 | 턴의 `completion_reports`(M8-T6). 개수와 첫 보고의 `step_id` |
| 테스트 파일 변경 | 턴의 모든 단계(서브에이전트 안 포함)에서 `test_edit`가 있는 도구 호출. 개수, 실패 직후 변경 수, 첫 변경의 단계 `id` |

실패 수는 세션 정보 상자의 실패 수와 같은 범위(주 에이전트의 도구 호출)를 센다.

### 7.2 배치

```text
 ◆                       압축┆              ◆                      ← 기호 줄
 [#1][#2 ✕2][#3][#4][#5][#6] ┆ [#7][#8 ✕1][#9][#10][#11 ✕6][#12]   ← 턴 칸
 턴 너비: [같게 | 걸린 시간에 비례]   #8 · 테스트 고쳐 · 도구 24 · 실패 1 · 4분 12초
```

- **턴 칸**: 턴마다 높이 28px의 칸 하나를 차례로 놓고, 칸 사이에 2px을 띈다. 칸 너비는 기본이 같은 너비(띠 너비 ÷ 턴 수)이고, 전환하면 걸린 시간에 비례한다(최소 6px).
- **색**: 실패 턴은 빨강 칸이고 칸 안에 `✕실패 수`를 쓴다. 나머지 턴은 회색 칸이다. 실행 중인 턴은 파랑 점선 테두리다. 색만으로 구분하지 않도록 ✕ 글자를 함께 쓴다([색과 접근성](../research/VisualizationPrinciples.md#49-색과-접근성)).
- **글자**: 칸 너비가 28px 이상이면 칸 안에 `#순번`을 쓰고, 실패 턴은 그 뒤에 `✕개수`를 쓴다. 좁으면 글자를 빼고 마우스를 올려 본다.
- **기호 줄**: 작업 중 사용자 메시지가 있는 턴의 칸 위에 노란 ◆를 둔다(흐름 그래프와 같은 모양, I39). 완료 보고가 있는 턴의 칸 위에는 ⚑를 둔다(M8-T6). 둘 다 있으면 나란히 둔다. 대화 요약(문맥 압축)이 일어난 턴은 칸 왼쪽에 점선 세로선과 "대화 요약" 글자를 둔다.
- **고른 턴**: 파랑 굵은 테두리.
- 띠 아래 한 줄에 마우스를 올린(없으면 고른) 턴의 순번, 턴 시작 지시의 첫 줄, 도구 호출 수, 실패 수, 걸린 시간, 작업 중 사용자 메시지 수를 적는다.

### 7.3 이동 배지

띠 위에 배지를 둔다: `실패한 턴 3 ◀ ▶`, `작업 중 사용자 메시지가 있는 턴 2 ◀ ▶`, `대화 요약이 일어난 턴 1 ◀ ▶`, `완료 보고가 있는 턴 4 ◀ ▶`, `테스트 파일을 바꾼 턴 2 ◀ ▶`(뒤의 둘은 M8-T6). 배지와 기호에 마우스를 올리면 대화 요약의 뜻("대화가 길어져 Claude Code가 앞 대화를 요약문으로 바꾼 턴. 이 뒤로 에이전트는 앞의 세부 내용을 요약으로만 기억합니다")이 나온다.

- ▶는 고른 턴보다 뒤에 있는 그 종류의 첫 턴을, ◀는 앞에 있는 마지막 턴을 고른다. 고른 턴이 없으면 ▶는 첫 턴, ◀는 마지막 턴이다. 개수가 0이면 단추를 끈다.
- **완료 보고가 있는 턴**으로 가면 그 턴의 첫 보고 단계를, **테스트 파일을 바꾼 턴**으로 가면 첫 테스트 파일 변경 단계를 함께 고른다.
- **실패한 턴**으로 가면 그 턴의 첫 실패 단계도 고른다. 흐름 그래프는 그 노드를 고른 상태로 열고, 목록은 그 단계를 강조한다(7.5절).
- 단축키: `]` 다음 실패한 턴, `[` 이전 실패한 턴. 입력 칸이나 선택 상자에 초점이 있으면 동작하지 않는다.

### 7.4 상호작용과 상태

| 동작 | 결과 |
| --- | --- |
| 턴 칸을 누름 | 그 턴을 고르고, 고른 단계를 지운다 |
| 배지 ◀ ▶, `[` `]` | 7.3의 규칙으로 턴(과 첫 실패 단계)을 고른다 |
| 턴 너비 전환 | 같은 너비와 걸린 시간 비례를 바꾼다 |

- 해시 상태: `turn`(고른 턴), `step`(고른 단계 `id`), `width`(`time`이면 걸린 시간 비례).
- 처음 만든 안의 범위 고르기(`from`·`to`)와 순서·실제 시간 축(`axis`)은 뺐다. 턴 상자가 턴 하나만 보여 주므로 여러 턴에 걸친 범위는 아래 보기에 쓸 곳이 없고, 턴 안의 시간은 흐름 그래프의 시간축이 맡는다.
- 해시에서 프로젝트·세션이 바뀌지 않았으면 세션 상세를 다시 받지 않고 마지막 응답으로 다시 그린다. 그래프 응답도 턴마다 기억한다. 새로고침 단추는 모두 다시 받는다. 배지로 연달아 이동할 때 매번 세션 전체를 다시 계산하지 않기 위해서다.

### 7.5 아래 보기 연결

개요 띠는 [세 층](VisualEncoding.md#2-화면-구성)의 집계 층이고, 턴 상자의 흐름 그래프와 단계 목록은 원본 층이다.

- **턴 고르기**: 개요 띠와 턴 선택 상자는 같은 `turn`을 바꾼다. 어느 쪽에서 골라도 둘이 함께 바뀐다.
- **목록 보기**: 고른 턴의 단계를 늘어놓고, 고른 단계가 있으면 강조(파랑 테두리)한 뒤 화면 안으로 스크롤한다.
- **흐름 그래프**: 고른 턴의 그래프를 그리고, 고른 단계가 있으면 그 노드를 고른 상태로 시작한다(노드 상세가 열린다). 노드 `id`는 단계 `id`이므로([그래프 모델의 노드](FlowGraph.md#32-노드)) 그대로 찾는다.
- 턴 선택 상자에서 다른 턴을 고르면 고른 단계를 지운다.
- 고른 단계가 노드 `id`가 아니면(`model` 노드의 둘째 이후 단계, 예: 완료 보고가 든 글 단계) 그 단계를 `step_ids`에 담은 노드를 고른다.

### 7.6 완료 보고 목록과 테스트 파일 변경 목록

[E11·E12](VisualEncoding.md#311-e11-완료-보고-표시와-목록)의 세션 수준 목록이다(M8-T6). 세션 전체 흐름 상자의 턴 너비 줄 아래에 접고 펴는 목록 두 개를 둔다. 기본은 접혀 있고, 편 상태는 실시간 갱신으로 다시 그려도 유지한다.

```text
 ▸ 완료 보고 목록 (5)
     #2  로그인 화면을 추가했습니다.                         응답 글(추정)
     #4  ☑ API 테스트 작성                                   할 일(확정)
 ▸ 테스트 파일 변경 목록 (3)
     #5  tests/test_cart.py   직전 테스트: 실패(2 failed, 68 passed)   ← 굵게
     #7  tests/test_api.py    직전 테스트: 통과   Bash에서 추정
```

- 한 줄이 보고 하나 또는 변경 하나다. 턴 순서, 그 안에서 단계 순서다.
- 줄을 누르면 그 턴과 그 단계를 고른다(7.5절). 흐름 그래프에서는 그 노드가 열린다.
- 완료 보고의 출처는 글자로 적는다: 응답 글은 `응답 글(추정)`, 할 일 도구는 `할 일(확정)`이다.
- 테스트 파일 변경은 경로(프로젝트 기준), 직전 테스트 실행의 결과와 요약을 적는다. 실패 직후 변경은 줄을 굵게 하고 앞에 `✕ 뒤`를 붙인다. 추정 변경은 `Bash에서 추정`을 붙인다.
- 목록이 비면 `없음`을 쓴다.

## 8. 실시간 갱신

진행 중인 세션을 Claude Code 옆에 띄워 두고 보도록, 서버가 바뀐 세션을 알리고 화면이 그 세션을 다시 그린다(M4-T2). 데이터는 이미 실시간으로 쌓인다. hook 이벤트가 도구 호출마다 들어오고, 그때마다 세션 기록도 이어 읽는다([기록 리더의 hook 이벤트를 받을 때](Transcript.md#41-hook-이벤트를-받을-때-m2-t3)).

### 8.1 변경 알림 스트림

`GET /api/stream`은 SSE(`text/event-stream`) 응답이다. 코드는 [서버 앱](../../src/agentvis/server.py#create_app)과 [stream_changes](../../src/agentvis/server.py#stream_changes)다.

- 연결되면 그때의 마지막 이벤트 `id`를 기억한다. 그 뒤 1초([STREAM_POLL_SECONDS](../../src/agentvis/server.py#STREAM_POLL_SECONDS))마다 [이벤트 저장소의 changes_since](Store.md#10-m4-t2-변경)로 새 이벤트를 묻는다.
- 새 이벤트가 있으면 `event: change`, `data: {"sessions": [바뀐 세션 ID…], "last_id": n}`을 보낸다. 1초 동안 들어온 이벤트는 한 알림으로 묶인다.
- 15초([STREAM_KEEPALIVE_SECONDS](../../src/agentvis/server.py#STREAM_KEEPALIVE_SECONDS)) 동안 보낼 것이 없으면 연결 유지용 주석 줄(`: keepalive`)을 보낸다.
- 연결이 끊기면(브라우저가 닫히거나 다른 세션으로 감) 묻기를 멈춘다. 서버가 종료 중이면(앱의 `state.stopping`, [CLI 설계의 serve](Cli.md#2-명령)) 스스로 끝나 연결을 닫는다.
- 저장소를 묻는 일은 스레드 풀에서 해 이벤트 루프를 막지 않는다. 다른 경로와 같이 `Host` 검사를 받는다.
- 저장소를 직접 묻는 방식이라, hook으로 들어온 이벤트와 기록 리더가 읽은 이벤트가 모두 같은 길로 알려진다.

### 8.2 화면의 갱신

화면은 `EventSource("/api/stream")`로 알림을 받는다. 코드는 `app.js`다.

| 받은 알림 | 하는 일 |
| --- | --- |
| 보고 있는 세션이 바뀜 | 그 세션 상세와 고른 턴 그래프를 다시 받아 그린다. 이미 받는 중이면 끝난 뒤 한 번만 더 받는다. |
| 보고 있는 프로젝트의 세션 목록에 영향이 있을 수 있음(바뀐 세션이 있음) | 세션 목록과 프로젝트 목록을 다시 받는다. 목록 계산이 무거우므로(실측 약 1.1초) 15초에 한 번까지만 한다. |
| 연결이 끊겼다가 다시 이어짐 | 끊긴 동안 놓친 알림이 있을 수 있으므로 새로고침 단추와 같이 모두 다시 받는다. |

**지키는 것**: 다시 그려도 사용자가 보던 상태는 그대로다.

- 고른 턴, 고른 단계, 보기 방식, 시간축은 해시에 있으므로 그대로다.
- 흐름 그래프의 가로 배율과 가로 스크롤 위치는 세션·턴·시간축마다 기억해 다시 그릴 때 되살린다. 처음 그릴 때만 `전체 보기` 배율을 쓴다.
- 목록 보기에서 고른 단계로 스크롤하는 것은 고른 단계가 바뀔 때만 한다. 알림으로 다시 그릴 때는 스크롤을 옮기지 않는다.
- 그래프에서 노드를 누르면 그 노드의 단계를 해시의 `step`에 둔다. 다시 그려도 노드 상세가 남는다. 실시간 따라가기가 켜져 있었으면 함께 끈다(아래).

**실시간 따라가기**(I42): 진행 중인 작업의 가장 최근 지점을 따라간다. 머리 줄의 새로고침 단추 옆 **실시간 따라가기 단추**로 켜고 끈다. 기본은 켜짐이다.

| 상태 | 보이는 턴 | 고른 노드(단계) | 화면 위치 |
| --- | --- | --- | --- |
| 켜짐 | 마지막 턴. 새 턴이 시작되면 그 턴으로 넘어간다 | 그 턴에서 주 에이전트 줄의 가장 최근 노드(시작 시각이 가장 늦은 노드). 노드 상세가 열린다 | 그래프는 그 노드가 화면 오른쪽 4분의 1쯤에 오도록 가로 스크롤을 옮긴다(배율은 그대로). 목록 보기는 그 단계로 스크롤한다 |
| 꺼짐 | 끈 순간 보던 턴에 머문다 | 끈 순간 고른 노드에 머문다 | 사용자가 둔 그대로 |

- 꺼져 있어도 알림이 오면 보던 턴의 내용은 다시 그려 최신으로 둔다. 보는 위치만 저절로 움직이지 않는다.
- **자동으로 꺼짐**: 켜진 상태에서 사용자가 마지막 턴이 아닌 턴을 고르거나(턴 칸, 턴 선택 상자, 이동 배지) 그래프의 노드를 직접 누르면 따라가기를 끈다. 고른 것을 다음 알림이 곧바로 빼앗지 않게 하기 위해서다. 실시간 로그 도구의 "끝 따라가기"(`tail -f` 류)가 사용자가 위로 스크롤하면 멈추는 것과 같다.
- **다시 켜기**: 단추를 누르면 고른 턴과 단계를 지우고 최신 턴·최신 노드로 간다.
- **해시 상태**: 켜짐은 `turn`·`step`이 없는 상태이고, 꺼짐은 `live=off`와 함께 그때의 `turn`·`step`을 적는다. 그래서 따라가기를 끈 화면의 주소를 공유하면 같은 턴·노드가 열린다.
- **단추 표시**: 켜짐은 `● 실시간 따라가기`(초록), 꺼짐은 `○ 따라가기 꺼짐`(회색)이다. 서버와 연결이 끊기면 상태와 관계없이 `○ 연결 끊김`(경고 색)으로 바뀌고, 다시 이어지면 원래 표시로 돌아온다. 마우스를 올리면 지금 상태와 누르면 무엇이 되는지 설명이 나온다.
- 턴 선택 상자에는 켜짐이면 `● 최신 턴과 최신 노드를 따라가는 중`을 적는다. 꺼짐이면 적지 않는다(켜는 곳은 맨 위 단추 하나다).

**실행 중인 막대**: 끝나지 않은 막대는 지금까지 받은 가장 늦은 시각까지 그린다. 알림이 올 때마다 다시 그려지므로 실행 중인 막대가 늘어난다. 알림 없이 오래 실행되는 도구(긴 테스트 등)는 다음 알림까지 늘어나지 않는다.

### 8.3 테스트

- `tests/test_store.py`: `changes_since`([저장소 설계 10절](Store.md#10-m4-t2-변경)의 테스트).
- [tests/test_api.py](../../tests/test_api.py): `stream_changes`가 새 이벤트가 들어오면 바뀐 세션을 담은 `change` 알림을, 새 이벤트가 없으면 연결 유지 줄을 내보내고, 연결이 끊기거나 서버가 종료 중이면 끝난다. 시간 간격은 테스트에서 줄인다.
- 화면 동작은 실제 서버와 진행 중인 세션으로 확인한다.

## 9. 실험 모드

I60에서 만든다. [실험 모드](Cli.md#22-experiment)(`agentvis experiment`)로 띄운 서버에서만 화면 사용 기록을 남긴다. 평소의 `serve`에서는 아무것도 기록하지 않는다. 기록은 참가자 컴퓨터의 [실험 데이터 디렉터리](Store.md#1-데이터-디렉터리)에만 남고, 연구자가 실험 뒤 그 파일을 받는다. 정량 분석(과업마다 걸린 시간, 어디를 거쳐 답에 닿았나)에 쓴다.

### 9.1 무엇을 남기나

화면 상태는 주소의 해시(프로젝트, 세션, 턴, 단계, 보기)에 있으므로, 해시가 바뀔 때마다 남기면 고른 세션·턴·노드가 모두 남는다. 여기에 사용자의 입력 자체를 더한다.

| 종류(`type`) | 언제 | `detail` |
| --- | --- | --- |
| `open` | 화면을 열 때 | `hash`, `path`(주소의 경로), 창 크기(`width`, `height`) |
| `hash` | 해시가 바뀔 때(세션·턴·단계 선택, 보기 전환, 배지 이동, 목록 줄 누름이 모두 여기에 남는다) | `hash` |
| `click` | 누를 때 | 누른 요소의 설명: 태그, `id`, 앞 두 개의 클래스, 글자 앞 60자 |
| `change` | 선택 상자(턴 고르기 등)를 바꿀 때 | 요소 설명, 고른 값 |
| `key` | 입력 칸 밖에서 수정 키 없이 키를 누를 때(배지 단축키 등) | `key` |
| `visibility` | 탭을 떠나거나 돌아올 때 | `state`(`hidden`·`visible`) |
| `scroll` | 화면을 굴릴 때, 2초에 한 번(M11-T1) | `y`(세로 위치), `ratio`(문서 높이에 대한 비율) |
| `find` | Ctrl+F·⌘F를 누를 때(M11-T1) | 없음 |
| `trial_start`, `trial_end` | 머리줄의 `시행 시작`·`시행 끝` 단추를 누를 때(M10-T6) | `trial`(1부터 세는 시행 번호) |

- 모든 항목에 브라우저 시각 `at`(ISO 8601)을 붙인다.
- 화면은 항목을 모아 두었다가 2초마다, 그리고 탭을 떠날 때(`fetch`의 `keepalive`) 보낸다([interaction.js](../../src/agentvis/web/interaction.js)). 보내기에 실패한 항목은 다음에 다시 보낸다.
- 실험 모드이면 머리줄에 `실험 모드 · <참가자>`를 보인다. 연구자가 실험 전에 바른 모드로 띄웠는지 확인하기 위해서다.
- **시행 표시**(M10-T6): 실험 모드이면 머리줄에 `시행 1 시작` 단추를 둔다. 누르면 `trial_start`를 남기고 단추가 `시행 1 끝`으로 바뀐다. 다시 누르면 `trial_end`를 남기고 번호가 하나 올라 `시행 2 시작`이 된다. 시작·끝은 곧바로 보낸다(2초를 기다리지 않는다). 과업마다 걸린 시간을 진행자의 손 기록 없이 화면 사용 기록에서 바로 얻기 위해서다. 새로고침하면 번호는 1로 돌아가므로, 진행자는 블록마다 서버를 다시 띄운다([진행 대본](../study/Protocol.md)).
- 글자 앞 60자에는 시나리오 세션의 내용이 들어갈 수 있다. 시나리오 세션은 실험용으로 만든 자료라 개인정보가 없다(I26).

### 9.2 API와 기록 파일

| 경로 | 동작 | 응답 |
| --- | --- | --- |
| `GET /api/experiment` | 실험 모드인지 알려 준다. | `{"participant": "<번호>" 또는 null, "version": "<AgentVis 버전>", "condition": "agentvis" \| "baseline" \| null}` |
| `POST /api/interactions` | 본문 `{"events": [{"at", "type", "detail"}, …]}`를 기록 파일에 한 줄씩 덧붙인다. | 성공: `{"stored": N}`. 실험 모드가 아니면 `404`. 검증 실패는 아래 표 |

요청 검증은 [수집기의 요청 검증](Collector.md#21-요청-검증) `Host` 검사 뒤에 다음을 본다. 다른 웹 페이지가 참가자 브라우저를 통해 기록을 오염시키지 못하게 하기 위해서다.

| 조건 | 실패 응답 |
| --- | --- |
| `Origin`이 `http://<Host 헤더 값>`과 같다(같은 출처의 화면에서 보낸 요청). | `403` |
| `Content-Type`의 미디어 타입이 `application/json`이다. | `415` |
| 본문이 [MAX_BODY_BYTES](../../src/agentvis/interaction.py#MAX_BODY_BYTES)(64KB) 이하의 JSON 객체이고 `events`가 [MAX_EVENTS](../../src/agentvis/interaction.py#MAX_EVENTS)(200개) 이하의 목록이다. 각 항목의 `type`은 영문 소문자·`_` 1\~32자, `at`은 40자 이하 문자열, `detail`은 JSON으로 2,000자 이하의 객체다. | `400`, 아무것도 저장하지 않음 |

본문 검사는 [parse_events](../../src/agentvis/interaction.py#parse_events)가 하고, 틀리면 [InvalidInteractions](../../src/agentvis/interaction.py#InvalidInteractions)를 낸다.

[InteractionLog](../../src/agentvis/interaction.py#InteractionLog)`(path, participant)`가 기록 파일 `<실험 데이터 디렉터리>/interactions.jsonl`에 쓴다.

- 서버가 시작할 때 `{"type": "server_start", "participant", "version", "condition", "received_at"}` 한 줄을 쓴다. 같은 참가자로 다시 띄우면 이어 쓰므로, 이 줄이 실행 구간을 나눈다. 버전은 [유저 스터디 기준판 규칙](../PullRequestRule.md#6-릴리스)대로 참가자가 쓴 버전을 남기기 위해서다.
- 항목마다 `{"received_at", "participant", "at", "type", "detail"}` 한 줄을 쓴다. `received_at`은 서버 시각이다.
- 여러 요청이 동시에 와도 줄이 섞이지 않게 잠금 안에서 쓴다.

### 9.3 테스트

- [tests/test_interaction.py](../../tests/test_interaction.py)
  - 실험 모드 앱에서 `GET /api/experiment`가 참가자와 버전을, 평소 앱에서는 `participant: null`을 돌려준다.
  - 같은 출처의 올바른 요청이 기록 파일에 항목마다 한 줄로 남고, 서버 시작 줄이 맨 앞에 있다.
  - 시행 표시 단추를 두 번 누르면 `trial_start`(시행 1)와 `trial_end`(시행 1)가 남고 단추가 `시행 2 시작`이 된다(헤드리스 Chrome으로 확인).
  - `Origin`이 없거나 다르면 `403`, `Content-Type`이 다르면 `415`, 형식이 틀린 본문(목록이 아님, 너무 많은 항목, 잘못된 `type`, 너무 긴 `detail`, 너무 큰 본문)은 `400`이고 아무것도 저장하지 않는다. 평소 앱에서는 `404`다.
- 화면의 기록 전송은 실험 모드 서버를 띄워 브라우저로 누르고, 기록 파일을 확인한 결과를 완료 기록에 남긴다.
- [tests/test_interaction.py](../../tests/test_interaction.py) (M11-T1): 기준선 앱의 `/`가 기록을 `기록 n`으로 나열하고 세션 ID 말고는 이름을 보이지 않으며, `/baseline/{세션}`이 머리줄·스크립트와 이스케이프된 기록을 돌려주고, 폴더에 없는 세션은 `404`다. 평소 앱에는 `/baseline/…`이 없다. `/api/experiment`의 조건이 맞다.

### 9.4 기준선 조건 (M11-T1)

`agentvis experiment … --baseline`으로 띄운 서버는 AgentVis 화면 대신 기준선 텍스트 기록 보기를 준다.

| 경로 | 내용 |
| --- | --- |
| `GET /` | 기록 목록([render_index](../../src/agentvis/study/baseline.py#render_index)). 기록마다 `기록 1`, `기록 2`…(세션 ID 순서)로 링크한다. 변형 이름이나 세션 ID의 뜻을 보이지 않는다 |
| `GET /baseline/{세션 ID}` | 그 기록의 텍스트 보기([실험 자료 도구 설계의 기준선](Study.md#4-기준선-텍스트-기록-보기-m9-t4), `experiment=True`). 시나리오 폴더에 있는 세션만 열고, 없으면 `404` |

- 텍스트 보기 위쪽에 AgentVis 조건과 같은 머리줄(실험 모드 표시, `시행 n 시작`·`끝` 단추)을 두고, 같은 [interaction.js](../../src/agentvis/web/interaction.js)로 화면 사용을 남긴다. 주소 해시가 없으므로 `hash` 대신 `open`이 어느 기록을 열었는지(`path`)를 남긴다.
- 두 조건 모두에서 `scroll`(2초에 한 번, 세로 위치와 문서 높이에 대한 비율)과 `find`(Ctrl+F·⌘F를 누름)를 남긴다. 기준선에서는 브라우저 찾기가 주된 탐색 수단이라, 찾기를 몇 번 썼는지가 비교 지표가 된다.
- `GET /api/experiment`는 조건(`condition`: `agentvis`·`baseline`)도 돌려준다.
- 기준선 조건에서도 AgentVis의 API와 정적 파일 경로는 그대로 있지만, 참가자에게는 `/`만 연다.
