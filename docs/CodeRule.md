# 코드 작업 규칙

이 문서는 프로젝트의 모든 코드 작업에 적용되는 규칙이다. 목적은 코드 개발을 일관되고 지속 가능하게 유지하는 것이다. 전체 문서 목록은 [문서 인덱스](index.md)에서 확인한다.

## 1. 문서 우선 작업 절차

모든 코드 작업은 아래 순서를 따른다. 순서를 바꾸지 않는다.

1. [문서 인덱스](index.md)에서 작업과 관련된 문서를 찾아 읽는다.
2. 작업의 ID를 정하고 시작 처리를 한다. [로드맵](Roadmap.md)의 태스크나 [이슈](Issue.md)여야 하며, 없으면 먼저 등록한다. 상태 변경과 [진행 중](Ongoing.md) 기록은 [작업 관리 규칙](TaskRule.md#41-시작)을 따른다.
3. 작업 내용을 규정하는 문서가 없거나 부족하면, [문서 작업 규칙](DocumentationRule.md)에 따라 문서를 먼저 작성·수정한다.
   - 상세 설계 문서(`docs/design/`)에는 구현할 모듈, 클래스, 함수와 그 동작을 적는다. 작업을 시작하기 전까지 구현 심볼은 인라인 코드로 적어 둔다.
   - 작업을 시작하면 그 작업에서 구현할 심볼을 [포인터 규약](Traceability.md)의 코드 포인터 링크로 바꾼다. 이 시점에는 코드가 없으므로 [포인터 검사기](VerificationTools.md#4-포인터-검사기)가 실패한다. 이 실패는 "문서가 요구하지만 아직 구현되지 않은 것"의 목록으로 쓴다.
4. 문서의 지시에 따라 코드를 작성한다. 각 코드에는 근거 문서로 가는 포인터를 단다.
5. [검증 도구](VerificationTools.md)를 모두 실행해 통과시킨다.
6. [작업 관리 규칙](TaskRule.md#43-완료)에 따라 완료 처리를 한다.

코드를 먼저 바꾼 뒤 문서를 코드에 맞추는 일은 하지 않는다. 구현 중 문서와 다른 방식이 필요하다고 판단되면 코드 작성을 멈추고 문서부터 고친다.

## 2. 디렉터리 구조

| 경로 | 용도 |
| --- | --- |
| `docs/` | 모든 문서. 코드 작업의 규칙이다. |
| `src/` | 제품 코드. 패키지 구성과 기술 스택은 [시스템 구조](Architecture.md#7-코드-구성)를 따른다. |
| `tools/` | 개발용 도구(검증 스크립트 등). [검증 도구](VerificationTools.md)에 규정된다. |
| `tests/` | 자동 테스트. |
| `pyproject.toml`, `.python-version`, `uv.lock` | uv 프로젝트 설정. [3. 언어와 스타일](#3-언어와-스타일)을 따른다. |

새로운 최상위 디렉터리가 필요하면 이 표를 먼저 수정한다.

## 3. 언어와 스타일

- 기본 언어는 Python이다.
- Python은 **반드시 uv 환경에서** 사용한다.
  - Python 버전은 uv가 관리하며 `.python-version`(현재 `3.12`)과 `pyproject.toml`의 `requires-python`으로 고정한다.
  - 모든 Python 실행은 `uv run`을 거친다. 시스템 Python(`python3`)이나 직접 만든 가상 환경을 쓰지 않는다.
  - 의존성은 `uv add`(개발용은 `uv add --dev`)로만 추가·제거한다. `pip`를 직접 쓰지 않는다. `uv.lock`은 저장소에 포함한다.
- `tools/`의 코드는 표준 라이브러리만 사용한다.
- 스타일은 PEP 8을 따른다.
  - 모듈·함수·변수 이름은 `snake_case`, 클래스는 `PascalCase`, 상수는 `UPPER_SNAKE_CASE`.
  - 모듈 내부 전용 심볼은 이름 앞에 `_`를 붙인다.
- 모든 함수의 인자와 반환값에 타입 힌트를 단다. `list[str]`, `str | None` 같은 내장 문법을 쓴다.
- 함수 하나는 한 가지 일만 한다. 같은 로직이 두 곳 이상에 생기면 공통 모듈로 옮긴다.
- 사용하지 않는 코드, 주석 처리된 코드는 남기지 않는다.
- 주석은 "무엇"이 아니라 "왜"를 적는다. 동작 설명은 문서에 있어야 한다.

## 4. 문서-코드 추적성

문서와 코드는 양방향 포인터로 연결한다. 형식과 규칙은 [포인터 규약](Traceability.md)을 따른다. 요약하면 다음과 같다.

- 문서는 마크다운 링크로 코드의 특정 심볼(AST 단위)을 가리킨다.
- 코드는 docstring 또는 주석으로 근거 문서를 가리킨다.
- 모든 모듈과 공개 최상위 클래스·함수는 근거 문서를 가리켜야 한다.
- 한쪽 방향 포인터만 있는 상태는 허용하지 않는다.

## 5. 테스트

- 테스트는 `tests/` 아래에 `test_<대상 모듈>.py` 이름으로 둔다.
- 테스트 프레임워크는 표준 라이브러리 `unittest`를 사용한다.
- 문서에 규정된 공개 동작마다 정상 경우와 실패 경우를 각각 하나 이상 테스트한다.
- 테스트도 코드이므로 [포인터 규약](Traceability.md)을 동일하게 적용한다. 테스트 모듈은 자신이 검증하는 동작을 규정한 문서를 가리킨다.

## 6. 검증과 완료 조건

코드 작업은 아래 명령이 모두 성공(종료 코드 0)해야 완료로 본다. 실행 방법의 상세는 [검증 도구](VerificationTools.md#1-실행-방법)에 있다.

```sh
uv run python -m tools.check_docs
uv run python -m tools.check_pointers
uv run python -m tools.check_tasks
uv run python -m unittest discover -s tests -t .
```

검증이 실패한 상태로 작업을 끝내지 않는다. 실패를 해결할 수 없으면 실패 내용을 그대로 보고한다.

## 7. 변경과 유지보수

- 동작을 바꾸려면 그 동작을 규정한 문서를 먼저 고친다. 그 다음 코드를 고친다.
- 심볼의 이름이나 위치를 바꾸면 [포인터 검사기](VerificationTools.md#4-포인터-검사기)가 깨진 포인터를 알려 준다. 문서의 포인터를 먼저 새 이름으로 고친 뒤 코드를 바꾼다.
- 심볼을 삭제하면 그 심볼을 가리키던 문서 내용도 함께 삭제하거나 고친다.
