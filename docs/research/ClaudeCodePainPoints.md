# Claude Code 바이브 코딩 실무 고충 조사

이 문서는 Claude Code로 바이브 코딩·에이전트 코딩을 할 때 실무자들이 겪는 고충을 커뮤니티 반응과 연구로 조사한 결과다. [제품 비전의 연구 목적](../ProductVision.md#1-목적)에 따라, AgentVis가 무엇을 추려 보여 줘야 하는지와 유저 스터디 과제를 무엇으로 할지의 근거로 쓴다. 시각화 쪽 근거는 [좋은 시각화 원칙 조사](VisualizationPrinciples.md)에 있다. 관련 작업은 이슈 I25다. 전체 문서 목록은 [문서 인덱스](../index.md)에서 확인한다.

## 1. 조사 방법과 한계

2026-10-31에 웹 조사 서브에이전트가 수집했고, 이 문서는 그 보고를 정리했다. 아래 한계를 감안해 읽는다.

- **GitHub 이슈**(`anthropics/claude-code`): GitHub API로 이슈별 반응(reactions)·댓글 수를 직접 조회했다. 표의 "반응"은 2026-10-31 기준 값이다. 4절에 "본문 확인"으로 표시한 이슈만 본문을 열었다.
- **Hacker News**: 점수는 Algolia API로 확인했다. 스레드 2개를 열었지만 앞부분만 읽었고, 인용은 웹 요약을 거쳤으므로 논문에 쓸 때는 원문과 대조해야 한다.
- **Reddit**: reddit.com에 직접 접근하지 못해 미러 스냅샷 2건만 확인했다. Reddit 쪽 빈도 신호는 약하다.
- **X(Twitter)**: 조사하지 못했다.
- **논문·설문**: 초록과 공식 페이지 수준으로만 확인했다.
- 검색 결과에만 보이고 열어 보지 못한 출처는 인용하지 않았다.

## 3. 작업 기록으로 관찰할 수 있는가

AgentVis가 모으는 데이터([데이터 소스](../DataSource.md))로 각 고충이 드러나는지와, 시각화가 보여 줄 수 있는 것이다. 신호의 판정 규칙은 아직 정하지 않았으며, 화면 개선 설계에서 [진단 신호](../ProductVision.md#3-진단-신호)와 함께 정한다.

| 고충 | 관찰 | 드러내는 신호 | 시각화가 보여 줄 것 |
| --- | --- | --- | --- |
| A 지시 무시 | 부분 | 사용자 메시지의 정정 표현("아니", "I said", "CLAUDE.md 읽었어?"), 중단 직후 정정, 규칙이 금지한 명령의 실행, 같은 정정의 반복 | 사용자 정정을 타임라인에 표시하고 직전 행동과 잇는다. |
| B 근거 없는 성공 보고 | 예(강함) | 마지막 테스트 실행 뒤의 Edit·Write, 파이프된 테스트 명령, 좁힌 실행(`-k`), 최종 응답의 "통과·완료" 주장과 실제 종료 코드·출력의 불일치. #104504가 세션 기록만으로 이 분석을 했다. | 최종 주장 옆에 그 주장을 뒷받침하는 실행과 신선도(그 뒤 편집 수)를 보이고, 근거 없는 주장에 경고를 단다. |
| C 목표 바꿔치기 | 예 | 테스트 실패 직후 테스트 파일 편집, `skip`·`xfail`·assert 삭제, 빌드·테스트 설정 변경, `mock`·`fallback`·`New*` 식별자 추가 | 실패에서 테스트 파일 수정으로 이어지는 흐름을 강조하고, 소스·테스트·설정별 변경 지도를 그린다. |
| D 압축 뒤 맥락 손실 | 예 | 문맥 압축 경계 이후의 정정, 같은 실패의 재발, 이미 읽은 파일의 재읽기 | 압축 경계를 긋고 전후 행동을 비교한다. 압축 전 대화를 다시 볼 수 있게 한다. |
| E 가시성 | 예(도구의 핵심 가치) | 읽은 경로, 생각 블록, 서브에이전트 기록, 백그라운드 작업 상태 | 파일 접근 지도, 서브에이전트 트리, 실시간 진행 |
| F 루프 | 예 | 비슷한 입력의 실패 반복, 같은 파일의 편집 왕복, 긴 무출력 구간, 같은 검색 반복 | 비슷한 호출을 묶고 반복 패턴과 그 시간을 보인다. |
| G 과잉 구현 | 부분 | 요청 대비 바뀐 파일·줄 수, 새 파일 수. 범위 판정은 지시의 의미에 달려 자동화가 어렵다. | 지시별 변경량 |
| H 조사 없이 편집 | 예 | 편집 전 그 파일을 읽었는지, Read:Edit 비율, Write 비중 | "읽지 않고 편집" 표시, 작업 단위 지표 |
| I 아첨 | 부분 | 정형 문구 뒤 행동이 실제로 바뀌었는지 | 우선순위 낮음 |
| J 권한 피로 | 예 | 권한 요청 횟수·간격, 같은 명령 재요청, 대기 시간 | 반복 요청 목록(보조 기능) |
| K 파괴적 행동 | 예 | `rm -rf`, `git reset --hard`, `stash`, `checkout --`, `--force`, 대량 삭제 | 위험 명령 강조와 영향받은 파일 |
| L 비용 | 부분 | 세션 기록의 토큰 사용량, 서브에이전트별 토큰. 남은 요금제 한도는 알 수 없다. | 단계·서브에이전트별 토큰 |
| M 리뷰 부담 | 부분 | 바뀐 파일 수, 변경 크기, 실행 길이. 신뢰는 유저 스터디 설문으로 잰다. | 의도 → 행동 → 결과 단위의 변경 요약 |

## 4. 시각화와 유저 스터디에 맞는 우선순위

조사 보고가 제안한 순서다. 이 순서는 화면 개선 설계에서 [좋은 시각화 원칙 조사](VisualizationPrinciples.md)와 함께 다시 검토한다.

1. **B 근거 없는 성공 보고 검증.** 고충이 크고, 세션 기록만으로 판정할 수 있다는 실증(#104504)이 있다. 과제 예: "에이전트가 '모든 테스트 통과'라고 보고한 세션에서 그 주장이 사실인지 판정하라." 정답이 분명해 정확도와 시간을 재기 좋다.
2. **C 테스트 변조·건너뛰기·mock 탐지.** 과제 예: "에이전트가 문제를 실제로 고쳤는가, 테스트를 바꿨는가?" 실험용 세션에 심어 넣기 쉽다.
3. **E·H 무엇을 했는지 파악.** 가시성 요구가 가장 직접적이다. 과제 예: "어떤 파일을 읽지 않고 고쳤는가?", "서브에이전트가 무엇을 했는가?"
4. **D 압축 전후 행동 변화.** 압축 경계는 데이터에 명시되어 있다. 과제 예: "언제부터 규칙을 어기기 시작했는가?"
5. **F 루프·반복 실패.** 과제 예: "시간을 낭비한 구간과 그 이유를 찾아라."
6. **A 지시 위반 지점.** 반응은 가장 많지만 자동 판정은 부분적이다. 과제 예: 규칙 목록을 주고 위반한 도구 호출을 찾게 한다. [제품 비전의 Q6](../ProductVision.md#2-핵심-분석-질문)과 맞닿는다.
7. **K 파괴적 행동 감사.** 드물지만 피해가 크고 바로 강조할 수 있다.

J(권한 피로)와 L(비용)은 고충은 크지만 시각화보다 설정·요금 문제에 가깝다.

연구 문헌은 공통으로 "에이전트 행동을 이해하고 검증하는 비용"을 문제로 본다(METR, Stack Overflow 2025, Kumar et al., Pimenova et al., Huang et al.). 그래서 유저 스터디의 종속 변수로 검증 정확도, 문제 위치를 찾는 시간, 신뢰 보정(주장과 사실에 대한 판단의 일치)이 맞는다.

**우리 데이터와의 대조**(2026-10-31, AgentVis 이벤트 저장소의 세션 전체):
- 턴 191개, 단계 3,169개, 도구 호출 1,293개 가운데 실패 표시 39건, 작업 중 사용자 메시지 18건이었다.
- 실패 39건에는 의미가 다른 것이 섞여 있었다.
  - 환경 문제: 명령 없음, 권한 거부
  - 검증이 문제를 찾은 것: 테스트 실패, 검사기 오류
  - 탐색 명령의 종료 코드 1
  - 도구 오용: 바꿀 내용 없는 Edit
- 따라서 실패 표시를 그대로 강조하기 전에 분류가 필요하다.
